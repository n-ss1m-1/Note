# Qt C/S航空订票系统（服务端）面试整理

# 项目背景

这是一个基于 Qt 的 C/S 航空订票系统，客户端负责界面与交互，服务端负责业务处理、网络通信和数据持久化。面试包装定位：**桌面端前台 \+ Qt/C\+\+ 服务端 \+ MySQL 数据库**的完整订票闭环系统，重点突出服务端核心职责：

- 用户认证与会话校验

- 航班查询与余座管理

- 订单创建、支付、取消、改签

- JSON 协议解析、TCP 拆包粘包处理

- 数据库事务保证订单与库存一致性

**一句话版本**：

这是一个基于 Qt Network 和 MySQL ODBC 的单体式 C\+\+ 服务端项目，客户端通过 TCP 发送 JSON 请求，服务端完成登录、航班查询、订单创建/支付/取消/改签等核心业务，并通过事务保证订单状态和余座扣减的一致性。

# 技术栈清单

服务端面试建议按「通信层 / 业务层 / 数据层」拆分讲解：

- 语言与框架：C\+\+、Qt 6

- 网络通信：Qt Network、QTcpSocket

- 数据交换：QJsonObject / QJsonDocument

- 数据库访问：Qt SQL、QODBC

- 数据库：MySQL

- 架构形态：单体式 C/S 架构

- 协议设计：JSON \+ \&\#39;\\n\&\#39; 分隔符

- 一致性手段：数据库事务 \+ 条件更新 SQL

## 主要服务端模块

- ClientHandler：连接管理、拆包、协议分发

- DBManager：数据库连接、SQL 封装、事务控制

- OnlineUserManager：在线用户状态维护

- Protocol/Models：统一协议字段和模型转换

# 服务端核心架构（三层结构）

## 1\. 通信接入层

由 ClientHandler 负责：

- 接收客户端 TCP 数据

- 把 readAll\(\) 追加到缓冲区 m\_buffer

- 按 \\n 循环切分完整消息

- 将每条 JSON 反序列化后分发到具体业务分支

- 统一把响应对象序列化为 JSON，再追加 \\n 回写 socket

核心价值：把「网络报文处理」和「数据库业务」解耦。

## 2\. 业务处理层

主要在 ClientHandler 中做路由分发，面试建议抽象为「业务服务层」讲解：

- 登录/注册/改密/改手机号

- 常用乘机人增删查

- 航班条件查询

- 订单创建、支付、取消、改签

- 登录态校验和权限校验（例：改签时校验“原订单用户”与“当前用户”一致，避免越权）

## 3\. 数据访问层

由 DBManager 负责：

- 管理 QODBC 数据库连接

- 封装通用 Query / update

- 提供事务接口：beginTransaction\(\) / commitTransaction\(\) / rollbackTransaction\(\)

- 提供领域数据操作方法：searchFlights、createOrder、payForOrder、cancelOrder、rescheduleOrder

## 4\. 在线会话层

由 OnlineUserManager 维护：

- 当前 handler 对应的在线用户

- 登录后登记，断开连接后移除

- 部分接口从这里拿当前用户信息，而非完全信任客户端传参（体现「服务端不能信任客户端」的意识）

# 客户端与服务端通信协议（高频追问）

## 协议格式

统一采用 JSON，顶层字段固定为：

- type：消息类型

- data：业务数据

- success：执行结果（成功/失败）

- message：提示信息

示例（请求）：

```json
{
  "type": "order_create",
  "data": {
    "flightId": 1001,
    "passengerName": "张三",
    "passengerIdCard": "..."
  }
}
```

响应格式一致，type 变为对应 response（例：order\_create\_response）。

## 协议分隔

每条消息末尾追加一个 `\n` 作为结束符。

核心优点：

- TCP 是字节流，无消息边界，多条 JSON 连发易粘包

- 换行符可显式定义「消息边界」，解析逻辑简单，适配课程项目和中小型服务端

## 粘包处理机制

服务端与客户端采用同一逻辑：

1. onReadyRead\(\) 读取本次 socket 收到的所有字节

2. 追加到缓冲区 m\_buffer

3. 循环查找 `\n`

4. 每找到一个换行符，截取一条完整消息并做 JSON 解析

5. 剩余半包数据保留在缓冲区，等待下次 readyRead

总结一句话：通过「应用层分隔符 \+ 累积缓冲区」的方式，为 TCP 字节流人为补齐消息边界，从而解决粘包和半包问题。

# 核心模块流程图（文字描述）

## 1\. 创建订单流程

客户端选航班和乘机人 → 发送 order\_create → 服务端校验登录态 → DBManager 开启事务 → 条件扣减 seat\_left → 查询航班信息 → 生成座位号/金额/状态 → 插入 orders → 提交事务 → 返回新订单

**关键点**：

- 先扣库存，再插订单

- 两步放在一个事务里，任何一步失败都回滚

## 2\. 支付订单流程

客户端发送 order\_pay → 服务端校验登录态 → 更新订单状态为 Paid → pending\_payment 置 0 → 返回支付成功

补充说明：当前支付是「状态更新式模拟支付」，没有接入真实支付网关（体现项目边界认知）。

## 3\. 取消订单流程

客户端发送 order\_cancel → 服务端校验登录态 → 开启事务 → 更新订单状态为 Canceled 且 pending\_payment=0 → 查询该订单 flight\_id → 对应航班 seat\_left\+1 → 提交事务 → 返回成功

**关键点**：

- 取消订单不是删订单，而是状态流转

- 恢复库存必须和状态变更在一个事务内完成

## 4\. 改签流程（面试重点）

客户端发送原订单 \+ 新航班信息 → 服务端校验登录态与订单归属 → 开启大事务 → 取消原订单 → 创建新订单 → 计算差价 → 更新新订单待支付金额和状态 → 提交事务 → 返回新订单和差价

# 订单模块深度拆解

## 一、创建订单

核心目标：保证「库存扣减」和「订单创建」一致。

服务端逻辑拆分为 4 步：

1. **扣减余座**：执行 SQL
update flight set seat\_left = seat\_left \- 1 where id = ? and seat\_left \&gt; 0

2. **判断扣减结果**：若影响行数为 0，说明无票或并发被抢完，回滚并返回失败

3. **构造订单**：查询航班信息，计算 seatNum = seatTotal \- seatLeft \+ 1、priceCents = pendingPayment = flight\.priceCents、status = Booked

4. **写入订单并提交事务**：插入 orders 表，拿到新订单 ID，提交事务

**面试表达模板**：

创建订单不是简单 insert 一条订单记录，而是「库存扣减 \+ 订单写入」的复合操作，所以我把它设计成事务。先通过条件更新 SQL 扣减余座，再落订单，任何一步失败都 rollback，避免出现有订单没扣票或者扣了票没生成订单的脏数据。

## 二、支付订单

核心：订单状态迁移（status = Paid，pending\_payment = 0）。

补充强调：这里的支付是业务状态模拟，没有对接第三方支付，更多体现的是订单状态机的设计。

## 三、取消订单

核心：「订单状态回退 \+ 库存归还」。

关键 SQL 思路：先更新订单状态为 Canceled（条件限制 status not in \(Canceled, Finished\)，避免重复取消），再根据订单关联航班恢复 seat\_left \+ 1。

面试追问应答：为什么先改订单状态再加库存？
因为取消订单的业务主语是订单本身，先保证订单进入终态，再归还库存；同时两步都在事务里，不会出现中间态对外可见的问题。

# 改签模块深度拆解（项目核心亮点）

## 1\. 改签的业务本质

改签不是简单修改订单行，而是「终止原订单 \+ 新建一张新订单 \+ 重新计算应付金额 \+ 处理差价」，保留订单流转痕迹，比直接 update 原订单更合理。

## 2\. 改签事务设计

整个改签流程被一个「大事务」包裹：

1. 计算原订单已支付金额：oriPaidAmount = oriPrice \- oriPendingPayment

2. 取消原订单：调 cancelOrder\(orderId, false\)（传 false 表示复用当前大事务，不单独开启）

3. 创建新订单：调 createOrder\(newOrder, false\)（复用当前事务）

4. 计算差价：priceDif = newOrder\.priceCents \- oriPaidAmount

5. 设置新订单待支付金额：newOrder\.pendingPayment = max\(0, priceDif\)

6. 更新新订单状态为 Rescheduled

7. 提交事务（中间任一步失败都 rollback）

## 3\. 面试高频追问：为什么用大事务包住取消和新建？

标准回答：因为改签本质上是一个原子操作，不能只取消原订单却没生成新订单，也不能生成了新订单却没取消原订单。如果拆成两个独立事务，就可能出现用户订单状态不一致、库存也不一致的问题。所以我把取消原订单和创建新订单放在同一个事务里，保证要么全部成功，要么全部失败。

## 4\. 差价计算逻辑（体现业务细节）

核心：原订单总价不一定全部支付，需用「原订单已实际支付金额」参与差价计算，而非原票面价。

公式：

- 原订单已支付金额：oriPaidAmount = oriPrice \- oriPendingPayment

- 差价：priceDif = newPrice \- oriPaidAmount

- 新订单待支付：max\(0, priceDif\)

# 技术难点与解决方案（STAR 法则）

## 1\. 并发与一致性：如何防止超卖

- **S（背景）**：航空订票场景下，多用户可能同时抢同一航班余票，若先查 seat\_left 再更新，高并发下会发生超卖。

- **T（任务）**：保证并发创建订单时，库存不被扣为负数，不生成超过余票数量的订单。

- **A（行动）**：采用「条件更新 SQL \+ 事务」方式，核心 SQL：
update flight set seat\_left = seat\_left \- 1 where id = ? and seat\_left \&gt; 0
将「判断有票」和「扣减一张票」合并为原子数据库操作，通过检查 numRowsAffected\(\) 判断是否抢到库存；若影响行数为 0，直接回滚退出，再在同一事务中插入订单记录。

- **R（结果）**：避免「先查后改」的竞态条件，基本防止超卖，保证单库单表场景下订单与库存的一致性。

进阶补充：该方案在单机单库下有效，面对更高并发或分布式部署，还需缓存预扣、队列削峰、分布式锁等进一步增强。

## 2\. 改签事务设计

- **S（背景）**：改签涉及原订单取消、新订单创建、库存回滚与重新扣减、差价计算，是跨多步骤的复合业务。

- **T（任务）**：保证改签过程对用户是原子的，不出现只取消不新建、重复占座等问题。

- **A（行动）**：将改签整体设计为大事务，先计算原订单已支付金额，再复用 cancelOrder\(false\) 取消原订单、createOrder\(false\) 创建新订单，最后计算差价并更新新订单状态；中途任一步失败则整体回滚。

- **R（结果）**：实现改签全流程一致性，保证订单状态、库存变化和差价计算在数据库层面同步。

## 3\. TCP 粘包处理

- **S（背景）**：TCP 是流式协议，不保证消息边界，多条 JSON 连发会粘包，消息过大会半包。

- **T（任务）**：让服务端稳定解析每一条 JSON 请求，不因粘包/半包导致解析失败或服务崩溃。

- **A（行动）**：应用层设计文本协议，规定每条 JSON 消息以 \\n 为结束标记；服务端 readyRead 后将数据追加到缓冲区，循环查找换行符，取出完整消息解析；解析失败仅记录日志，不主动断开连接。

- **R（结果）**：服务端可稳定处理连续请求，保留半包数据等待后续拼接，提升通信层健壮性。

## 4\. 数据库连接兼容性

- **S（背景）**：Qt 通过 QODBC 连接 MySQL 时，不同机器的 ODBC 驱动名可能不同，易出现「本机可用、他机不可用」的兼容性问题。

- **T（任务）**：提高数据库连接在不同环境下的可移植性和容错性。

- **A（行动）**：连接阶段不写死驱动名，尝试多个常见驱动名（例：MySQL ODBC 8\.0 Unicode Driver、MySQL ODBC 9\.5 Unicode Driver）；连接失败时，将 lastError\(\) 返回给上层，方便排查环境问题。

- **R（结果）**：提升项目在不同 Windows 开发环境中的兼容性，减少因 ODBC 驱动版本差异导致的连接失败。

# 高频面试题（Q/A）

- **Q1：你的服务端架构是什么？**
A：这是一个基于 Qt 的单体式 C/S 服务端。ClientHandler 负责 TCP 接入、JSON 解析和请求分发，DBManager 负责数据库访问和事务控制，OnlineUserManager 负责登录态与在线用户管理。网络层、业务层、数据层基本有清晰边界。

- **Q2：为什么协议选 JSON？**
A：JSON 可读性高、调试方便，Qt 原生支持 QJsonObject/QJsonDocument，适合课程项目和中小型系统快速开发。同时通过统一 type/data/success/message 顶层结构，前后端协议比较规范。

- **Q3：为什么还需要 \\n 分隔符？**
A：因为 TCP 是字节流，不自带消息边界。单独使用 JSON 并不能解决粘包半包问题，所以在应用层定义每条消息以 \\n 结束，再配合缓冲区按行拆包。

- **Q4：创建订单为什么要先扣库存再插订单？**
A：因为库存是稀缺资源，要优先通过条件更新抢占。如果先插订单再扣库存，失败后会产生无效订单。先扣库存、再插订单，并放到同一事务中，能更好保证一致性。

- **Q5：where seat\_left > 0 为什么能防止超卖？**
A：它把「校验有票」和「扣减库存」合成了一条原子 SQL，避免多个线程都先读到有票再分别扣减的竞态问题。只要数据库更新成功，说明当前事务拿到了这张票；如果影响行数为 0，就表示票已经没了。

- **Q6：这个方案能完全应对秒杀场景吗？**
A：不能完全。它适用于单体、单库下的中低并发场景；真正秒杀级高并发下，数据库会成为瓶颈，还需要缓存预扣、消息队列削峰、分布式锁、热点隔离等方案。

- **Q7：改签为什么不直接 update 原订单？**
A：因为改签不是简单修改航班字段，而是一个新的交易行为。保留原订单并生成新订单，更符合订单系统的可追溯性，也便于处理差价和状态流转。

- **Q8：改签时差价为什么不是“新票价 \- 原票价”？**
A：因为原订单可能还没全部支付，真正应参与抵扣的是「原订单已支付金额」，即 原价 \- 待支付金额。这样才能正确反映用户还需补多少钱。

- **Q9：取消订单为什么不直接删除订单？**
A：订单属于业务凭证，应该保留历史记录。删除会丢失审计和追踪能力，所以采用状态流转，取消只是把状态置为 Canceled，并恢复库存。

- **Q10：服务端如何避免未登录用户伪造请求？**
A：多数业务接口都会先检查当前 ClientHandler 的登录态，并从在线用户管理模块获取用户信息，而不是完全依赖客户端上传的 userId。

# 系统设计题：面对高并发/秒杀，会有什么问题？（延展提问）

## 当前系统的潜在问题

1. **数据库成为瓶颈**：余座扣减强依赖数据库 update 操作，并发高时，热点航班行竞争激烈，数据库锁冲突和响应时间上升。

2. **单体架构扩展性有限**：网络接入、业务处理、数据库操作在一个单体服务中，扩容粒度粗，热点模块易拖垮整个服务，难以独立限流和隔离。

3. **缺少削峰填谷机制**：所有请求直接打到服务端和数据库，无消息队列或缓存层，高峰瞬时流量会直达 DB。

4. **一致性手段偏单机**：当前事务和条件更新 SQL 适合单机单库，多实例部署时，系统层面并发控制更复杂。

## 改进方案

1. **引入缓存预扣库存**：将热点航班余票放入 Redis，请求先到 Redis 扣减库存，扣减成功后异步落库，减轻数据库热点更新压力（注意：从强一致转向最终一致，需补充补偿机制）。

2. **加消息队列削峰**：下单请求先进入消息队列，前端快速返回“排队中”，后端消费者按顺序处理库存和订单，防止数据库被瞬时流量打爆。

3. **分布式锁或原子扣减**：多实例部署时，结合 Redis Lua 原子脚本、分布式锁或库存令牌预发放模型，控制热点航班并发扣减。

4. **拆分服务**：将单体架构拆分为用户服务、航班服务、订单服务、支付服务，热点模块单独扩容，提升系统弹性。

5. **增加幂等和补偿机制**：应对高并发下的重复请求、网络重试、异步失败，需设计下单幂等 token、订单状态机校验、失败补偿任务、库存回补机制。

## 推荐回答模板

当前项目在单体 \+ 单库场景下，通过事务和条件更新 SQL 已经能解决基本一致性问题，但如果面向秒杀级高并发，数据库会成为热点瓶颈，单体架构也不易扩展。优化方向上，我会优先考虑 Redis 预扣库存、消息队列削峰、分布式锁或 Lua 原子扣减，以及把订单和航班模块拆成独立服务。同时补充幂等控制和失败补偿，保证高并发场景下的稳定性和一致性。

这个项目的服务端是基于 Qt Network 和 MySQL ODBC 做的单体 C\+\+ 后端。客户端和服务端通过 TCP 传输 JSON，自定义用 \\n 作为消息分隔符，并通过缓冲区循环拆包来解决粘包问题。核心难点在订单和改签业务上，我把「扣减余座」和「创建订单」放进同一个事务里，并用 update \.\.\. where seat\_left > 0 防止超卖。改签则是一个更大的事务，里面包含取消原订单、创建新订单和差价计算，保证整个流程的一致性。
