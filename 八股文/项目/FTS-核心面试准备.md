##### 介绍一下你的项目(航班票务系统)
> 我主导开发了一个基于Qt的航空订票系统，采用客户端-服务端架构。客户端是Qt桌面应用，负责用户交互；我主要负责服务端开发，使用Qt Network和MySQL ODBC构建了一个高可用的后端系统。
> 
> **技术架构上**，我设计了三层架构：通信层通过QTcpSocket处理网络请求，使用自定义JSON协议并以'\n'作为分隔符解决TCP粘包问题；业务层处理核心订票逻辑；数据层通过ODBC连接MySQL，封装了事务控制和动态查询。
> 
> **核心难点在于数据一致性**。在订单创建时，我将"扣减余座"和"创建订单"封装在同一个事务中，通过条件更新SQL `UPDATE flight SET seat_left = seat_left - 1 WHERE id = ? AND seat_left > 0` 防止超卖问题。这个方案在单库场景下确保了库存与订单的强一致性。
> 
> **最复杂的是改签业务**。我设计了一个大事务，包含"取消原订单→创建新订单→计算差价→更新状态"四个步骤。特别在差价计算上，不是简单的票价差，而是基于"原订单已支付金额=原票价-待支付金额"来计算，确保资损风险最小化。
> 
> **项目成果**：系统支持完整的订票流程，包括用户管理、航班查询、订单生命周期管理。通过事务设计和协议优化，系统在测试中稳定处理了高并发场景，没有出现数据不一致问题。

###### JSON和粘包问题
## 1. 为什么选择JSON？

**可读性与开发效率**：JSON是文本格式，调试时可以直接看到请求内容，比二进制协议更友好。Qt原生支持QJsonObject和QJsonDocument，序列化/反序列化非常方便，适合快速迭代的项目。

**协议规范性**：我们统一了顶层字段结构——`type`（消息类型）、`data`（业务数据）、`success`（执行结果）、`message`（提示信息）。这样前后端字段不会错乱，降低了联调成本。

## 2. 为什么JSON不能解决粘包问题？

**关键认知**：TCP是字节流协议，不保证消息边界。即使每条消息都是完整的JSON，多个JSON连续发送时，TCP层可能把它们合并成一个数据包（粘包），或者把一个JSON拆成多个包（半包）。

**举个例子**：客户端连续发送两条消息：

```
1{"type":"login","data":{...}}\n
2{"type":"flight_search","data":{...}}\n
```

服务端的`readyRead()`可能一次读到两个JSON拼在一起的字符串，直接解析会失败。

## 3. 我们的解决方案：应用层分隔符 + 缓冲区机制

**核心设计**：在每条JSON末尾追加一个`\n`作为消息结束符。

**服务端拆包流程**：

```
1// 1. 累积数据到缓冲区
2m_buffer.append(m_socket->readAll());
3
4// 2. 循环查找分隔符
5while (m_buffer.contains('\n')) {
6    int idx = m_buffer.indexOf('\n');
7    QByteArray line = m_buffer.left(idx);  // 取出完整消息
8    m_buffer = m_buffer.mid(idx + 1);      // 剩余数据留到下次
9    
10    // 3. 解析JSON
11    QJsonDocument doc = QJsonDocument::fromJson(line);
12    if (doc.isObject()) {
13        handleJson(doc.object());
14    } else {
15        qWarning() << "JSON parse error";  // 容错：不中断连接
16    }
17}
```

**为什么这个方案有效？**

- **显式边界**：`\n`人为定义了消息边界，TCP的字节流被我们"切片"成独立消息
- **缓冲区容错**：半包数据会留在`m_buffer`中，等待下次`readyRead()`补齐
- **简单高效**：查找换行符的时间复杂度O(n)，对中小型系统足够快



###### 怎么保证数据一致性的？
## 1. 核心原则：事务原子性

所有涉及多个表更新的操作，都必须放在同一个事务中，确保"要么全部成功，要么全部失败"。
## 2. 典型场景一：订单创建（防超卖）
**为什么能防超卖？**

- **条件更新**：`WHERE seat_left > 0`确保只有余座>0时才更新
- **行锁机制**：MySQL的UPDATE会加行锁，其他事务必须等待
- **原子性**：扣座和建单在一个事务，不会出现"扣了座但没建单"的中间状态

## 3. 典型场景二：改签流程（大事务）

**问题**：改签涉及"取消原订单+创建新订单+计算差价"，任何一个步骤失败都会导致数据不一致。
**关键设计**：

- **事务嵌套控制**：`cancelOrder`和`createOrder`都支持`autoManageTransaction=false`，让外层统一管理事务
- **差价计算逻辑**：不是简单的新旧票价差，而是"新票价 - 原已支付金额"，避免资损
- **状态流转**：新订单状态设为`Rescheduled`，便于后续追踪

###### 订单全流程：订单创建/支付/取消/改签
- 创建订单(autoManageTransaction默认true 表示该函数内部开启事务 否则为外部开启事务->改签时复用)
	1. 开启事务
	2. 减少剩余座位数：update flight set seat_left=seat_left-1 where id=? and seat_left>0
	3. 座位不足/更新失败：回滚
	4. 根据flightId查询航班信息
	5. 初始化订单座位号
	6. 初始化订单价格和待支付价格
	7. 初始化订单状态：Booked
	8. 插入订单数据到order表
	9. 初始化订单id
	10. 提交事务
- 支付订单
	1. 开启事务
	2. 根据orderId：pendingPayment->0
	3. 提交事务
- 取消订单(autoManageTransaction默认true 表示该函数内部开启事务 否则为外部开启事务->改签时复用)
	1. 开启事务
	2. 根据orderId：update订单状态->取消
	3. 退钱
	4. 根据orderId查询对应的flightId
	5. 根据flightId更新剩余座位数+1
	6. 提交事务
- 改签
	1. 开启整体事务
	2. 保存old_order已支付价钱
	3. 取消原订单(复用接口)
	4. 改原订单状态->rescheduled
	5. 创建新订单(复用接口)
	6. 差价=新订单价格-原已支付价钱
	7. pendingPayment=max(0, 差价)
	8. 根据pendingPayment更新新订单的状态->Booked or Paid
	9. 提交事务(其中某步失败则回滚)
