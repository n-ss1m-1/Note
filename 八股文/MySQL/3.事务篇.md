# 事务基础(ACID四大特性)
#### 原子性(Atomicity)
- 定义：事务内所有操作「要么全成功，要么全失败」，不允许中间状态
- InnoDB实现方式：`undo log`(回滚日志) ->事务失败时通过 undo 日志回滚到初始状态

#### 一致性(Consistency)
- 定义：事务执行前后，数据始终满足完整性约束(如转账前后总金额不变)
- InnoDB实现方式：由原子性 + 隔离性 + 持久性共同保证

#### 隔离性(Isolation)
- 定义：多个并发事务互不干扰，各自有独立的执行空间
- InnoDB实现方式：`MVCC`(多版本并发控制) + 锁机制

#### 持久性(Durability)
- 定义：事务提交后，数据修改永久生效，系统故障也不丢失
- InnoDB实现方式：`redo log`(重做日志)->事务提交前写入 redo 日志，崩溃后通过 redo 恢复


# 并发事务的三大问题
#### 1. 脏读（Dirty Read）
- **定义**：一个事务「读取了另一个未提交事务修改的数据」，若对方回滚，读到的就是过期 / 无效数据。
- **例子**：事务 A 给小林余额 + 100 万（未提交），事务 B 读到了 200 万，随后 A 回滚，B 拿到的就是脏数据。

#### 2. 不可重复读（Non-repeatable Read）
- **定义**：同一个事务内，**多次读取同一条数据，结果前后不一致**（因为中间被其他事务修改并提交了）。
- **例子**：事务 A 第一次读小林余额 100 万，事务 B 修改为 200 万并提交，A 再次读取时变成 200 万，同一事务内两次结果不同。

#### 3. 幻读（Phantom Read）
- **定义**：同一个事务内，**多次执行相同范围查询，结果集行数不一致**（中间被其他事务插入 / 删除了数据）。
- **例子**：事务 A 查询余额 > 100 万的账户共 5 条，事务 B 插入 1 条符合条件的数据并提交，A 再次查询时变成 6 条，像「出现了幻觉」。

#### 读已提交（read committed）

- 定义：事务执行期间看到的数据，始终和事务启动时一致

	- **MySQL `InnoDB` 默认隔离级别**

- 定义：事务完全串行执行，一个事务执行完，下一个才能执行

# 事务隔离级别的实现方式：多版本并发控制(MVCC)
#### 1. MVCC 核心原理
- MVCC 是 `InnoDB` 实现「读已提交」「可重复读」隔离级别的核心
- 通过**版本链 + Read View(一致性视图)** 实现无锁并发读，大幅提升并发性能。

#### 2. 聚簇索引中的 两个核心隐藏列
`InnoDB` 会给每一行聚簇索引记录自动添加两个隐藏列，是 MVCC 的基础：
- `trx_id`：最后一次修改这条记录的事务 ID
- `roll_pointer`：回滚指针，指向这条记录的上一个历史版本，串联成**版本链**(undo log)

#### 3. Read View的 4 个核心字段
Read View 是事务执行快照读（普通 `SELECT`）时，生成的「当前数据库事务状态视图」，用来判断记录的哪个版本对当前事务可见：
- `m_ids`：当前数据库中 **活跃(未提交)** 的事务 ID 列表
- `min_trx_id`：`m_ids` 中最小的事务 ID（活跃事务的最小 ID）
- `max_trx_id`：**下一个要分配**的事务 ID（全局最大事务 ID +1）
- `creator_trx_id`：创建这个 Read View 的当前事务 ID

![[Read_View字段.PNG|446]]



#### 4. 版本可见性判断规则
事务读取记录时，会遍历版本链，用 Read View 判断每个版本是否可见：
1. **若记录 `trx_id < min_trx_id`**：修改这条记录的事务在当前事务启动前就已提交，**可见**
2. **若记录 `trx_id >= max_trx_id`**：修改这条记录的事务在当前事务启动后才启动，**不可见**
3. **若 `min_trx_id <= trx_id < max_trx_id`**：
    - 若 `trx_id` 在 `m_ids` 中：修改记录的事务是活跃事务（未提交），**不可见**
    - 若 `trx_id` 不在 `m_ids` 中：修改记录的事务已提交，**可见**

#### 5. 「可重复读」vs「读已提交」的核心区别
两者都基于 MVCC 实现，唯一区别是 **Read View 的创建时机**：

- **可重复读（Repeatable Read）**：事务**启动时**创建一次 Read View，整个事务期间都复用这个视图 → 事务内所有查询看到的都是事务启动时的数据，解决了不可重复读
- **读已提交（Read Committed）**：事务**每次执行 SELECT 时**，都重新创建一个新的 Read View → 能看到其他事务刚提交的修改，存在不可重复读


#### InnoDB的两种事务启动方式(生成Read View的时机不同)
- `BEGIN / START TRANSACTION`：
	- 执行第一条 `SELECT` 时才真正启动事务，生成 Read View
	
- `START TRANSACTION WITH CONSISTENT SNAPSHOT`：
	- 执行命令时立即启动事务，生成 Read View




# InnoDB可重复读隔离级别，完全解决幻读了吗？
#### 核心结论
MySQL `InnoDB` 默认的**可重复读（Repeatable Read, RR）隔离级别，并没有 100% 彻底解决幻读，只是极大程度上避免了幻读的发生**，仅在极端特殊场景下会出现幻读。


#### 什么是幻读？
幻读是并发事务的三大问题之一，官方定义为：
 - 同一个事务内，多次执行**相同范围的查询语句**，前后两次查询的**结果集行数**不一致
 - (比如第一次查 5 条，第二次查 6 条，出现了 “幻觉” 一样的新行 / 少行)，就称为幻读。


#### `InnoDB` RR 级别下，如何避免幻读？

##### 1. 快照读(普通 `SELECT` 语句)：通过 MVCC 解决
- **原理**：可重复读隔离级别下，事务**启动时会生成一个固定的 Read View（一致性视图）**，整个事务期间的所有快照读，都复用这个视图。
- **效果**：事务内所有查询看到的，永远是事务启动时的历史数据，其他事务插入 / 修改的新数据，对当前事务完全不可见，从根源避免了幻读。
- **例子**：事务 A 两次查询`id>2`的记录，中间事务 B 插入新数据，事务 A 两次查询结果完全一致，无幻读。

##### 2. 当前读(`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT`)：通过 next-key lock 解决
- **原理**：当前读会读取最新数据，InnoDB 给查询范围加 **next-key lock（记录锁 + 间隙锁的组合）**，不仅锁住已存在的记录，还锁住记录之间的「间隙」，阻止其他事务在该范围内插入新数据。
- **效果**：其他事务无法在加锁范围内插入新行，彻底避免了当前读场景下的幻读。
- **例子**：事务 A 执行`SELECT * FROM t WHERE id>2 FOR UPDATE`，会锁住`(2, +∞)`的范围，事务 B 无法插入`id=5`的新记录，避免幻读。


#### 为什么说「没有完全解决幻读」？两个极端场景？

##### 场景 1：快照读的特殊穿透（事务内更新触发可见性变化）
1. 事务 A 执行快照读：`SELECT * FROM t WHERE id=5`，此时表中无`id=5`的记录，结果为空。
2. 事务 B 插入`id=5`的记录并提交。
3. 事务 A 执行当前读更新：`UPDATE t SET name='xxx' WHERE id=5`（当前读会读取最新数据，成功更新这条记录）。
4. 事务 A 再次执行快照读：`SELECT * FROM t WHERE id=5`，此时能查到这条记录，前后两次查询结果不一致，发生幻读。
- **原因**：事务 A 的 UPDATE 操作会把新记录的`trx_id`修改为自己的事务 ID，导致后续快照读时，这条记录对事务 A 可见，打破了 MVCC 的一致性。

##### 场景 2：当前读的延迟加锁（先快照读，后当前读）
1. 事务 A 执行快照读：`SELECT * FROM t WHERE id>100`，得到 3 条记录。
2. 事务 B 插入`id=200`的记录并提交。
3. 事务 A 执行当前读：`SELECT * FROM t WHERE id>100 FOR UPDATE`，得到 4 条记录，前后两次结果不一致，发生幻读。
- **原因**：事务 A 先做了无锁的快照读，事务 B 成功插入数据；后续事务 A 做当前读时，会读取最新数据，导致结果集变化。

#### 如何彻底避免极端场景的幻读？
- **开启事务后，立即执行 `SELECT ... FOR UPDATE` 这类当前读语句
- **->对查询范围加 next-key lock（记录锁 + 间隙锁），从根源阻止其他事务插入新数据，彻底避免幻读**
