# MySQL有哪些锁？

#### 全局锁

###### 定义
全局锁是**整个数据库实例级**的锁，加锁后整个库进入**只读状态**，所有写操作（DML/DDL）都会被阻塞
###### 加锁 / 解锁命令
- 加锁：`FLUSH TABLES WITH READ LOCK`（简称 FTWRL）
- 解锁：`UNLOCK TABLES`
- 自动释放：会话断开时自动释放
###### 作用
**全库逻辑备份**（如 `mysqldump`），保证备份期间数据一致性，避免备份过程中数据 / 表结构变更导致备份文件不一致
###### 缺点与替代方案
- **缺点**：加锁期间业务完全只读，会造成业务停摆，影响可用性
- **替代方案**：
    - 支持事务的引擎（如InnoDB）：用 `mysqldump --single-transaction`，基于 MVCC 实现一致性读，无需加全局锁，不影响业务
    - 不支持事务的引擎（如MyISAM）：必须用全局锁备份


#### 表级锁

| 锁类型         | 核心作用                   | 加锁方式                         |
| ----------- | ---------------------- | ---------------------------- |
| 表锁（共享 / 独占） | 手动加表级读写锁               | `LOCK TABLES ... READ/WRITE` |
| 元数据锁（MDL）   | 保护表结构，防止 CRUD 与 DDL 冲突 | 自动加锁，无需手动调用                  |
| 意向锁         | 表级标记，快速判断是否有行锁         | 自动加锁，无需手动调用                  |
| AUTO-INC 锁  | 保证自增主键连续性              | 自动加锁，控制自增锁模式                 |
##### 表锁
###### 分类与命令
- **共享锁（读锁）**：`LOCK TABLES t_test READ`
    - 本会话：可读该表，**不可写**，也**不可访问其他表**
    - 其他会话：可读该表，不可写（写操作阻塞）
    
- **独占锁（写锁）**：`LOCK TABLES t_test WRITE`
    - 本会话：可读写该表，**不可访问其他表**
    - 其他会话：所有读写操作完全阻塞
###### 特点
- 锁粒度大，并发性能差，**InnoDB中尽量避免使用**，仅MyISAM常用。
- 加锁后限制本会话操作范围，只能操作锁定的表，**访问其他表直接报错**。
- 解锁：`UNLOCK TABLES` 或会话断开自动释放。

##### 元数据锁(MDL， Metadata Lock)
###### 作用
**自动保护表结构**：保证CRUD 操作和表结构变更(DDL)不会同时执行，避免数据不一致

###### 加锁 / 解锁规则
- 执行 CRUD（SELECT/INSERT/UPDATE/DELETE）：**自动**加 **MDL 读锁**
- 执行 DDL（ALTER TABLE/DROP TABLE）：**自动**加 **MDL 写锁**
- 读锁与读锁兼容，读锁与写锁互斥，写锁与写锁互斥
- **事务提交后：自动解锁**

###### 特性
- 优先级：**MDL写锁>MDL读锁**，若MDL写锁被长事务MDL读锁阻塞，则后续的MDL读锁也将被阻塞
- 无需手动调用，MySQL 自动管理，是InnoDB表结构安全的核心保障


##### 意向锁
###### 作用
**表级标记锁**，用于**快速判断**「表中是否存在行锁」，**避免逐行检查**，提升加锁效率

###### 分类与对应关系
- **意向共享锁（IS）**：事务准备对表中**行加共享锁**前，先在表上加 IS 锁
- **意向独占锁（IX）**：事务准备对表中**行加独占锁**前，先在表上加 IX 锁

###### 兼容性规则
- **意向锁之间互相兼容**（IS 与 IX、IS 与 IS、IX 与 IX 不冲突）
- **意向锁与表级锁互斥**：
    - 表加共享锁（READ）：会阻塞表上的 IX 锁（即阻塞行写锁）
    - 表加独占锁（WRITE）：会阻塞表上的 IS/IX 锁（即阻塞所有行锁）

###### 手动加锁方式
- 加行共享锁：`SELECT ... LOCK IN SHARE MODE`（自动加表 IS 锁）
- 加行独占锁：`SELECT ... FOR UPDATE`（自动加表 IX 锁）

##### AUTO-INC锁
###### 作用
保证自增主键（`AUTO_INCREMENT`）的**连续性**，插入数据时为自增字段加锁，分配自增值

###### 锁模式(`innodb_autoinc_lock_mode` 控制)

| 模式值   | 锁类型            | 特点                                 | 适用场景                                  |
| ----- | -------------- | ---------------------------------- | ------------------------------------- |
| **0** | 传统 AUTO-INC 表锁 | **语句执行完才释放锁**，自增连续，并发性能差           | 兼容旧版本，批量插入保证连续                        |
| **1** | 轻量级锁           | **普通插入**申请自增后**立即释放**，**批量插入仍持表锁** | 平衡性能与连续性，**默认值**                      |
| **2** | 轻量级锁           | 申请自增后**立即释放**，并发最高，自增可能不连续         | 高并发插入，需配合 `binlog_format=ROW` 避免主从不一致 |
###### 注意事项
- **模式 2** 搭配 `binlog_format=STATEMENT` 会导致主从数据不一致，必须用 **`ROW` 格式**
	- 考虑两个并发的批量插入：
	- 1.主表插入：
		- 分别持有锁，然后获取自增id
		- 此时对其中任意一个插入语句来说，每次插入的id不是连续的
		- 如果搭配`binlog_format=STATEMENT` (只记录两个插入的SQL语句)
	- 2.从表复制：
		- 进行主从复制时，顺序执行两个SQL语句
		- 此时对其中任意一个插入语句来说，每次插入的id都是连续的
- 生产推荐：`innodb_autoinc_lock_mode=2` + `binlog_format=ROW`，兼顾并发与一致性



#### 行级锁

| 锁类型               | 锁定对象     | 核心作用             | 触发场景             | 兼容性                       |
| ----------------- | -------- | ---------------- | ---------------- | ------------------------- |
| **Record Lock**   | 单行记录     | 防止修改 / 删除单行      | 唯一索引 + 精准匹配      | X 与 X/S 互斥，S 与 S 兼容       |
| **Gap Lock**      | 记录间的间隙   | 防止插入新记录，解决幻读     | 非唯一 / 范围 / 无索引查询 | 间隙锁之间互相兼容                 |
| **Next-Key Lock** | 记录 + 前间隙 | 彻底解决幻读，防止修改 / 插入 | 默认行锁算法（RR 级别）    | X 型 Next-Key Lock 互斥      |
| **插入意向锁**         | 插入位置的点   | 标记插入意图，判断间隙冲突    | `INSERT`操作       | 与 Gap Lock 互斥，插入意向锁之间互相兼容 |
##### 定位
行级锁是**InnoDB存储引擎独有** 的锁机制（**MyISAM不支持**），是InnoDB高并发性能的核心保障。
- 锁粒度最小：仅锁定**单行记录**，最大程度减少锁冲突
- 支持事务：锁在事务提交 / 回滚后**自动释放**
- 普通 `SELECT` 是**快照读**（MVCC），**不加锁**
- 只有**当前读**(`SELECT ... FOR UPDATE` / `SELECT ... LOCK IN SHARE MODE`)、**写**(`UPDATE`/`DELETE`/`INSERT`) 才会**加行锁**

##### 基础分类(S锁/X锁)
###### 共享锁（S 锁，Shared Lock）
- **加锁方式**：`SELECT ... LOCK IN SHARE MODE`
- **兼容性**：读读兼容，读写互斥，写写互斥
- 多个事务可同时对同一行加 S 锁，但加 S 锁后，其他事务无法加 X 锁（无法修改）

###### 独占锁（X 锁，Exclusive Lock）
- **加锁方式**：`SELECT ... FOR UPDATE`、`UPDATE`/`DELETE`/`INSERT`
- **兼容性**：完全互斥（X 与 X、X 与 S 均不兼容）
- 一个事务加 X 锁后，其他事务无法对该行加任何锁，只能等待锁释放

##### Record Lock(记录锁)
- **本质**：锁定**单行记录本身**，**不锁定间隙**
- **作用**：防止其他事务修改 / 删除该行记录
- **触发场景**：
    - 唯一索引 + 精准匹配（如 `WHERE id = 1`，id 为主键 / 唯一索引）
- **示例**：`SELECT * FROM t_test WHERE id = 1 FOR UPDATE;` 对`id=1`的记录加 X 型记录锁

##### Gap Lock(间隙锁)
- **本质**：锁定**记录之间的间隙**，**不包含记录本身**
- **核心作用**：解决**幻读**问题（可重复读隔离级别下，防止其他事务在间隙中插入新记录）
- **触发场景**：
    - 非唯一索引、范围查询、`LIKE`模糊查询、无索引查询
    - 唯一索引 + 范围查询（如 `WHERE id > 3`）
- **特点**：
    - 间隙锁之间**互相兼容**（多个事务可对同一间隙加 Gap Lock，不冲突）
    - 仅阻止**插入操作**，**不阻止删除** / 修改已存在的记录
- **示例**：表中`id`为`[1,3,5,6]`，`WHERE id > 3`会锁定`(3,5)`、`(5,6)`、`(6,+∞)`三个间隙，阻止插入`id=4`、`id=7`等记录

##### Next-Key Lock(临键锁，Record Lock + Gap Lock)
- **本质**：**记录锁 + 间隙锁的组合**，锁定「**记录本身 + 记录前的间隙**」，是InnoDB的RR隔离级别下**默认的行锁**
- **核心作用**：彻底解决幻读，同时防止其他事务修改 / 插入记录
- **锁定规则**：
    - 对于索引上的每一条记录，锁定 ( 前一个索引值 , 当前索引值 ] 的区间
    - 例如`id`为`[1,3,5,6]`，Next-Key Lock 的区间为`(-∞,1]`、`(1,3]`、`(3,5]`、`(5,6]`、`(6,+∞]`
- **触发场景**：
    - 所有**非「唯一索引 + 精准匹配」的查询**，默认加 **Next-Key Lock**
    - **唯一索引 + 精准匹配**时，退化为 **Record Lock**（无间隙锁）
- **示例**：`SELECT * FROM t_test WHERE id = 5 FOR UPDATE;`（非唯一索引场景），会锁定`(3,5]`区间，既锁定`id=5`的记录，也阻止插入`id=4`的记录


##### 插入意向锁
- **本质**：特殊的**间隙锁**，属于行级锁，不是意向锁，锁定**插入位置的点**
- **作用**：标记「事务计划在某个间隙插入新记录」，用于间隙锁的冲突判断
- **特点**：
    - **与普通间隙锁互斥**：若间隙已被加 Gap Lock，插入意向锁会阻塞，等待锁释放
    - 多个事务可对同一间隙加**插入意向锁（互相兼容）**，仅等待间隙锁释放
- **触发场景**：**执行`INSERT`操作**时，自动加插入意向锁，判断插入位置是否被间隙锁占用


#### 行锁的核心规则与面试考点

###### 1. 加锁的前提

- 必须在**事务中**使用（`BEGIN`/`START TRANSACTION`），事务提交后锁自动释放
- 普通`SELECT`是快照读，不加锁；只有**当前读**（锁定读、写操作）才会加行锁

###### 2. 隔离级别对行锁的影响

- **可重复读（RR，InnoDB 默认）**：默认启用 Next-Key Lock，彻底解决幻读
- **读已提交（RC）**：关闭间隙锁，仅加 Record Lock，无法解决幻读，并发性能更高

###### 3. 索引对行锁的影响（核心考点）

- **有索引（唯一索引 + 精准匹配）**：加 Record Lock，仅锁定单行，并发最高
- **有索引（非唯一 / 范围查询）**：加 Next-Key Lock，锁定区间
- **无索引**：对全表加 Next-Key Lock（相当于表锁），严重影响并发，**生产绝对禁止**

###### 4. 幻读的解决

- 可重复读隔离级别下，InnoDB 通过**Next-Key Lock + MVCC** 彻底解决幻读
- 间隙锁阻止插入，MVCC 保证一致性读，双重保障






# MySQL是怎么加行级锁的？
#### 核心前提
- **隔离级别**：InnoDB默认 **可重复读（RR）**
- **默认加锁**：**开启事务**后，默认加 **Next-Key Lock（临键锁 = 记录锁 + 间隙锁）**，仅在满足条件时退化
- **加锁对象**：**索引**（不是数据行），扫描到的索引都会加锁
- **解锁时刻**：事务提交 / 回滚后才释放锁
- **终止扫描规则**：找到**第一个不满足条件的记录**后，停止扫描
- **特殊伪记录**：
	- infimum pseudo-record：最小记录，对应 `(-∞, 第一条记录]`
	- supremum pseudo-record：最大记录，对应 `(最后一条记录, +∞)`

#### 锁的查看命令
`SELECT * FROM performance_schema.data_locks\G;`
- `LOCK_TYPE = TABLE`：表级锁
- `LOCK_TYPE = RECORD`：行级锁
	- `LOCK_MODE = X`：X 型 Next-Key Lock
	- `LOCK_MODE = X,REC_NOT_GAP`：X 型记录锁
	- `LOCK_MODE = X,GAP`：X 型间隙锁


#### 唯一索引(主键 / 唯一二级索引)加锁规则

##### 二级索引加锁与主键索引加锁的区别
- **只要二级索引命中了记录(查到了行)    → 一定会同时锁：二级索引 + 对应的主键索引**
	
- **如果二级索引没命中任何记录(查不到) → 只锁二级索引的间隙，不锁主键索引**


##### 等值查询
- **查询的记录存在**：Next-Key Lock **退化为记录锁**，仅锁该行
- **查询的记录不存在**：Next-Key Lock **退化为间隙锁**，锁定**查询值所在的间隙**(`2`->`(1,5)`)

##### 范围查询
###### 1.> （大于）
- **示例**：`SELECT * FROM user WHERE id > 15 FOR UPDATE;`（id 为主键）
- **加锁过程**：
    1. 找到**第一个大于等于条件的记录** `id=20`，对其加 **Next-Key Lock** `(15, 20]`
    2. 继续扫描，直到 **`supremum pseudo-record`**，对其加 **Next-Key Lock** `(20, +∞)`
    3. 停止扫描
- **加锁结果**：3 个 X 型 Next-Key Lock，覆盖 `(15, 20]` 、`(15，20]`、`(20, +∞)`

###### 2. >=（大于等于）
- **示例**：`SELECT * FROM user WHERE id >= 15 FOR UPDATE;`（id 为主键）
- **加锁过程**：
    1. 找到**第一个大于等于条件的记录** `id=15`，因是等值查询且记录存在，**Next-Key Lock 退化为记录锁**，仅锁 `id=15` 单行
    2. 继续扫描 `id=20`，对其加 **Next-Key Lock** `(15, 20]`
    3. 扫描到最大记录 **`supremum pseudo-record`**，对其加 **Next-Key Lock** `(20, +∞)`
    4. 停止扫描
- **加锁结果**：4 个 X 型锁：记录锁：`id=15` 记录锁 + Next-Key Lock：`(15, 20]`+`(15，20]`+`(20, +∞)` 
- **核心区别**：
	- `>=` 场景中，**等值命中的第一条记录会退化为记录锁**，仅锁单行，不锁间隙
	- 无等值命中：与 `>` 场景相同

###### 3. <（小于）
- **示例**：`SELECT * FROM user WHERE id < 6 FOR UPDATE;`(**无论记录是否存在于表中**)
- **加锁过程**：
	1. **从最小记录 `infimum` 开始**，对每个扫描到的记录`id=x`加 **Next-Key Lock** `(-∞, x]`
	2. 扫描到**第一个大于等于条件的记录** `id=10`，**Next-Key Lock 退化为间隙锁 `(5, 10)`**
	3. 停止扫描
- **加锁结果**：3 个 X 型锁：`(-∞, 1]` Next-Key Lock + `(1, 5]` Next-Key Lock + `(5, 10)` 间隙锁
- **阻塞效果**：无法插入 `id=2/3/4`、`id=6/7/8/9` 的新记录，无法更新 / 删除 `id=1/5` 记录


###### 4. <=（小于等于）
1. 条件值**不存在**于表中：加锁规则与「`<` 条件值不存在」完全一致，最终加锁结果相同
	
2. 条件值**存在**于表中
	- **示例**：`SELECT * FROM user WHERE id <= 5 FOR UPDATE;`（表中有 `id=5`）
	- **加锁过程**：
	    1. 对 `id=1` 加 Next-Key Lock `(-∞, 1]`
	    2. 扫描到满足条件的记录 `id=5`，对其加 Next-Key Lock `(1, 5]`
	    3. 因 `id=5` 满足 `<=5`，继续扫描到第一个不满足条件的记录 `id=10`，停止扫描
	- **加锁结果**：2 个 X 型 Next-Key Lock：`(-∞, 1]` + `(1, 5]`
	- **核心区别**：`<=` 场景中，**条件值命中的记录会加完整 Next-Key Lock**，不会退化为间隙锁


#### 非唯一二级索引加锁规则
##### 二级索引加锁与主键索引加锁的区别
- **只要二级索引命中了记录(查到了行)    → 一定会同时锁：二级索引 + 对应的主键索引**
	
- **如果二级索引没命中任何记录(查不到) → 只锁二级索引的间隙，不锁主键索引**


##### 等值查询
1. 记录**不存在**的情况
	- **示例**：`SELECT * FROM user WHERE age = 25 FOR UPDATE;`（age 为非唯一索引，表中无 age=25 记录）
	- **加锁过程**：
		1. 扫描二级索引，找到**第一个大于条件的记录**（如 age=39）
		2. 该记录的 **Next-Key Lock 退化为间隙锁**，锁定区间 `(22, 39)`（仅锁间隙，不锁记录）
		3. 因无满足条件的记录，**不对主键索引加锁**
	- **加锁结果**：1 个 X 型间隙锁：`(22, 39)`

2. 记录**存在**的情况
	- **示例**：`SELECT * FROM user WHERE age = 22 FOR UPDATE;`（age 为非唯一索引，表中有 age=22 记录）
	- **加锁过程**：
	1. **二级索引（非唯一）**：
	    1. 对**满足条件的记录** `age=22` ，加 **Next-Key Lock** `(21, 22]`
	    2. 继续扫描，找到**第一个大于条件的记录**`age=39`，其 **Next-Key Lock 退化为间隙锁** `(22, 39)`
	    3. 停止扫描
	2. **相对应的主键索引**：
		4. 对所有满足条件的记录（如 `id=10`），加**记录锁（Record Lock）**
	- **加锁结果**：n 个 X 型Next-Key Lock + 1 个 X 型间隙锁：`(22, 39)` + n个X型记录锁

##### 范围查询?
- **示例**：`SELECT * FROM user WHERE age >= 22 FOR UPDATE;`（age 为非唯一索引）
- **核心特性**：非唯一索引范围查询**无退化**，**Next-Key Lock 不会退化为记录锁 / 间隙锁**，所有扫描到的索引都加完整临键锁
- **加锁过程**：
1. **二级索引（非唯一）**：
    1. 对**第一个等值匹配的记录**`age=22`，加 **Next-Key Lock** `(21, 22]`
    2. 对**第一个大于条件的记录**`age=39`，加 **Next-Key Lock** `(22, 39]`
    3. 扫描到最大记录 `supremum pseudo-record`，加 **Next-Key Lock** `(39, +∞)`
    4. 停止扫描
2. **相应的主键索引**：
	5. 对所有满足条件的记录（`id=10`、`id=20`），加**记录锁**
**加锁结果**：n 个 X 型 Next-Key Lock + m 个 X 型记录锁


#### 无索引查询（全表扫描）
- **加锁规则**：
	- 对**全表所有主键索引**加 Next-Key Lock
	- 效果等同于**表锁**，整张表阻塞，生产绝对禁止

# MySQL死锁了，怎么办？

#### 行级锁的概念回顾
##### 三种基础锁

| 锁类型                    | 作用                      | 兼容性                     |
| ---------------------- | ----------------------- | ----------------------- |
| **Record Lock(记录锁)**   | 锁定单行记录                  | X 与 X/S 互斥，S 与 S 兼容     |
| **Gap Lock(间隙锁)**      | 锁定索引间的间隙，防止插入，解决幻读      | 间隙锁之间互相兼容，与插入意向锁互斥      |
| **Next-Key Lock(临键锁)** | 记录锁 + 间隙锁的组合，InnoDB 默认锁 | X 型 Next-Key Lock 重叠就互斥 |
##### 插入意向锁
- 本质：**特殊的间隙锁**
- 生成时刻：执行insert语句时生成
- 作用：标记插入意图，判断插入位置是否被间隙锁占用，避免幻读
- 兼容性：
	- 插入意向锁 **与 间隙锁 / 临键锁 互斥**
	    → 间隙被锁 → 插入阻塞
	- 插入意向锁 **与 其他插入意向锁 兼容**
	    → 多个事务可以同时想插同一个间隙，不互相阻塞
	- 插入意向锁 **不与记录锁冲突**（只关心间隙）

##### 隐式锁与显式锁
- **隐式锁**：InnoDB的延迟加锁机制，插入记录时默认用隐式锁保护，无锁冲突时不生成显式锁，提升性能
- **显式锁**：当有其他事务请求锁时，隐式锁转为显式 X 型记录锁，触发阻塞
	- 场景：事务 A 插入order_no=1006，未提交时事务 B 插入相同值，A 的隐式锁转为 X 锁，B 加 S 型 Next-Key Lock 时冲突阻塞


#### Insert 语句的加锁规则
##### 1. 正常插入（无冲突）
- 用**隐式锁保护记录**，不生成显式锁，性能最优
- 仅当有其他事务请求锁时，隐式锁转为**显式 X 锁**

##### 2. 唯一键冲突场景
- **主键冲突**：对已存在的主键记录加 **S 型记录锁**
- **唯一二级索引冲突**：对已存在的二级索引记录加 **S 型 Next-Key Lock**
- 效果：其他事务对该记录执行 `select ... for update` 时，因 S 锁与 X 锁冲突被阻塞

##### 3. 间隙锁阻塞插入
- 若插入位置的间隙被加了 间隙锁 / Next-Key Lock，插入操作会生成**插入意向锁**，进入**等待状态**，直到锁释放



#### 死锁的四个必要条件
只要破坏任意一个条件，即可避免死锁：
- **互斥条件**：资源只能被一个事务持有，无法共享
- **持有且等待**：事务持有已获取的锁，同时等待其他事务持有的锁
- **不可强行剥夺**：事务持有的锁不能被强制剥夺，只能主动释放
- **循环等待**：多个事务形成闭环等待链，互相等待对方释放锁


#### 死锁的解决方案
##### 1. 超时自动回滚
- 参数：`innodb_lock_wait_timeout`，默认 50 秒
- 原理：事务等待锁超时后自动回滚，释放锁，让其他事务继续执行
- 缺点：超时时间难调，过长影响业务，过短易误回滚

##### 2. 主动死锁检测（默认开启）
- 参数：`innodb_deadlock_detect = on`
- 原理：InnoDB 主动检测死锁链条，回滚代价最小的事务，释放锁
- 优点：实时处理死锁，无需等待超时
- 缺点：高并发下检测消耗 CPU，可能影响性能


#### 死锁的预防方案
#### 1. 业务层面优化(推荐)
- **唯一索引替代幂等校验**：将`order_no`设为唯一二级索引，利用数据库唯一性保证不重复，彻底去掉`select ... for update`，从根源消除锁
- **统一加锁顺序**：多个事务操作相同资源时，按相同顺序加锁，避免循环等待
- **缩短事务持有锁时间**：尽快提交事务，减少锁的持有时间，降低死锁概率
- **避免长事务**：长事务会长期持有锁，大幅提升死锁风险

### 2. 数据库层面优化
- **调整隔离级别**：将 RR 隔离级别改为 RC（读已提交），关闭间隙锁，减少锁冲突（但会失去幻读防护，需业务保证）
- **避免无索引加锁**：无索引的`update/delete/select ... for update`会全表加 Next-Key Lock，等价于表锁，极易引发死锁
- **合理使用索引**：确保加锁查询走索引，避免全表扫描，缩小锁范围
