# 执行一条select语句期间发生了什么？(必须掌握)
#### 流程总览
- **客户端** → **连接器** → **查询缓存(8.0 已移除)** → **解析器** → **优化器** → **执行器** → **存储引擎（InnoDB）** → **磁盘 / 内存数据**
- MySQL 架构分为：
	- **Server 层**（负责连接、解析、优化、执行，通用功能）
	- **存储引擎层**（负责数据存储、索引实现，可替换，默认InnoDB）
	- 所有核心功能均由 Server 层完成，存储引擎层仅负责数据交互
- ![[执行select的流程.PNG]]


#### 1.连接器
###### 核心职责
- 建立 TCP 连接（三次握手）
- 管理连接
- 校验用户名 / 密码
- 分配权限（连接建立后权限静态生效，后续管理员改权不影响当前连接）


###### 连接类型对比
```
//短连接
连接mysql服务 (TCP三次握手)
执行sql
断开mysql服务 (TCP四次挥手)
......

//长连接
连接mysql服务 (TCP三次握手)
执行sql
执行sql
......
断开mysql服务 (TCP四次挥手)
```
- **长连接优点**：长连接可以减少建立连接和断开连接的次数，**一般建议使用长连接**
- **长连接缺点**：但是长连接可能导致**内存占用增多**
	- 连接对象的资源只有在连接断开时才会释放
	- ->长连接累积
	- ->MySQL占用内存过多，被系统杀死
- **长连接占用内存过高的问题的解决方法**：
	1. 定期断开长连接(定时执行`kill connection`)
	2. mysql客户端调用`mysql_reset_connection()`重置连接(仅释放内存，无需重连)

###### 实操验证命令
```
-- 查看当前连接列表
show processlist;

-- 查看空闲连接超时时间(默认 8 小时 / 28800 秒)
show variables like 'wait_timeout';

-- 查看最大连接数(默认151 超出则报错Too many connections)
show variables like 'max_connections';

-- 手动断开指定连接（ID 从 processlist 获取）
kill connection +6;

-- 重置长连接（释放内存，不中断业务）
mysql_reset_connection();
```


#### 2.查询缓存
###### 核心职责
- 查询语句如果命中查询缓存则直接返回
###### 致命缺陷
- **缓存失效极快**(表任意更新，该表所有缓存全清空)
- **全局锁竞争严重**，多核CPU下性能反而下降
- **MySQL 8.0彻底移除该模块**，5.7及之前版本默认关闭
###### 替代方案
- 应用层缓存(Redis) + 存储引擎层缓存(Buffer Pool)

#### 3.解析 SQL
###### 核心职责
- **词法分析**(识别关键字、表名、列名，拆分 Token)
- **语法分析**(校验 SQL 语法合法性，如关键字拼写错误)
- **构建抽象语法树**(AST)
注意：解析器**不校验表 / 字段是否存在**，仅负责语法合法性校验

#### 4.执行 SQL
##### 4.1 预处理阶段(Preprocess)
###### 核心职责
- 校验表 / 字段是否存在
-  将 `*` 解析扩展为具体列名

##### 4.2 优化阶段(Optimize・大脑)
###### 核心职责
- 基于 **成本模型** (IO 成本 + CPU 成本)选择 **最优执行计划** (如选哪个索引、多表 Join 顺序)
###### 分析工具
**`EXPLAIN` 命令查看执行计划**，重点关注 3 个字段：
- **`type`**：查询的类型(性能：`system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`)
	- `system`/`const`：最快的索引类型，主键 / 唯一索引等值查询，仅匹配 1 行
	- `eq_ref`：join 最优的关联类型，联表查询时，主键 / 唯一索引关联
	- `ref`：普通索引最优匹配类型，普通索引等值查询
	- `range`：索引范围查询（>/>=/</<=/in/between）
	- `index`：全索引扫描，比全表扫快一点
	- `ALL`：全表扫描，性能最差的类型
- **`key`**：实际使用的索引
	- `NULL` ：表示未使用索引
	- 不为`NULL`：索引生效 or 部分索引生效(只用到联合索引的部分字段)
- `key_len`：联合索引生效长度，用于判断联合索引到底用了几个字段
	- `int`：4 字节
	- `varchar(n)`：`n*3`(utf8)/ `n*4`(utf8mb4)+ 2 字节(长度标记)+ 1 字节(允许 NULL)
	- `bigint`：8 字节
	- `tinyint`：1 字节
- `rows`：预估扫描行数
- **`Extra`**：额外信息
	- `Using index`：**覆盖索引**，无需回表查询
	- `Using where`：索引过滤后，在 Server 层内存二次过滤(例：and其中一边无索引)
	- `Using index condition`：**索引下推（ICP）**，在索引层就过滤数据，减少回表次数
	- `Using filesort`：**文件排序**，`order by` 字段没走索引，在内存 / 磁盘排序(优化：给排序字段加索引)
	- `Using temporary`：**临时表**，`group by/distinct` 字段没走索引，生成临时表存中间结果(优化：给分组字段加索引)
	- `Using join buffer`：join 关联字段没加索引，用 join buffer 拼接结果(优化：给 join 关联字段加索引)


##### 4.3 执行阶段(Execute・操作工)
###### 核心职责
- 调用存储引擎 API，真正读取 / 写入数据
###### 三种执行场景
1. **主键索引查询**(最优)
	- 流程：执行器 → 存储引擎(B + 树定位主键)→ 内存 / 磁盘 → 返回结果；
	- 示例：`select * from product where id = 1;`(`type=const`，仅扫描 1 行)

2. **全表扫描**(性能最差)
	- 流程：执行器 → 存储引擎(全表遍历)→ 过滤条件 → 返回结果；
	- 示例：`select * from product where name = 'iphone';`(`type=ALL`，扫描全表)

3. **索引下推**(MySQL 5.6+ 优化策略)
	- **核心作用**：减少回表操作，将 Server 层的字段过滤逻辑下沉到存储引擎层；
	- **对比场景**：联合索引 `(age, reward)`，查询 `age > 20 and reward = 100000`；
	    - 无索引下推：存储引擎遍历二级索引，返回主键给 Server 层，**Server 层再回表校验 `reward`**(多次回表，性能低)
	    - 索引下推：存储引擎遍历二级索引时，**直接校验 `reward`**，过滤不满足条件的记录，**Server层仅回表满足条件的记录**(减少回表，性能高)
	- **识别标志**：执行计划 `Extra` 字段显示 `Using index condition`


#### 总结
MySQL 执行一条 `SELECT` 语句的流程，整体分为 **Server 层** 和 **存储引擎层** 两大模块，MySQL 8.0 已移除查询缓存，完整流程如下：
1. **连接器**：客户端发起连接，MySQL 完成 TCP 握手、账号密码校验，确认用户权限，连接建立后权限不会动态变更；
2. **解析器**：对 SQL 做词法分析、语法分析，判断语法是否合法，生成抽象语法树；
3. **预处理器**：检查表、字段是否存在，扩展 `*` 为具体列；
4. **优化器**：根据成本模型选择最优索引、确定多表连接顺序，生成最终执行计划( `EXPLAIN` 查看执行计划)；
5. **执行器**：根据执行计划调用存储引擎 API，校验操作权限，获取数据；
6. **存储引擎**：优先从 Buffer Pool 读取数据，未命中再访问磁盘，返回结果集给执行器，最终返回给客户端。



# InnoDB一行记录是怎么存储的？

#### MySQL的数据存放在哪个文件(必须掌握)

###### 存储层级(从大到小)

**表空间 (Tablespace)** ➔ **段 (Segment)** ➔ **区 (Extent)** ➔ **页 (Page)** ➔ **行 (Row)**

|结构单元|大小|核心作用|备注|
|:--|:--|:--|:--|
|**表空间**|逻辑概念|存放表数据、索引、元数据|对应 `.ibd` 文件（独立表空间）|
|**段**|-|数据段、索引段、回滚段|管理空间的逻辑单元|
|**区 (Extent)**|**1MB**|批量申请空间|解决页碎片化，保证顺序 I/O|
|**页 (Page)**|**16KB**|磁盘读写最小单位|I/O 操作以此为单位|
|**行 (Row)**|可变|实际业务数据|存放在页中|
###### 文件组成（InnoDB 独立表空间）
每个表对应两个文件：
- **`.frm`**：表结构定义文件(元数据)
- **`.ibd`**：表数据 + 索引文件(B+ 树)


#### InnoDB行格式有哪些？

|格式|版本|状态|核心特点|适用场景|
|:--|:--|:--|:--|:--|
|**Redundant**|5.0 前|废弃|紧凑性差，占用高|老旧系统|
|**Compact**|5.1 起|**主流**|紧凑，节省空间|**默认（5.7+）**|
|**Dynamic**|5.7 起|**推荐**|完全溢出存储，仅存指针|大字段、TEXT/BLOB|
|**Compressed**|-|特殊|压缩存储|对空间极度敏感|

#### Compact 行格式结构(必须掌握)

- 一条记录由 **额外信息** 和 **真实数据** 组成
- ![[Compact行格式结构.PNG]]
##### 记录的额外信息
1. **变长字段长度列表** (Variable Length List)
    - **作用**：存储 `VARCHAR` 等变长字段实际占用的字节数
    - **编码**：**逆序存放**(列顺序逆序)，**提升 CPU 缓存命中率**(真实数据和对应的字段长度信息可以同时在一个CPU Cache Line中)
    - **长度**：
	    - 没有变长字段时：省去变长字段长度列表
        - 最大长度 ≤ 255 Bytes：用 **1 字节** 表示
        - 最大长度 > 255 Bytes：用 **2 字节** 表示

2. **NULL 值列表** (NULL Bitmap)
    - **作用**：标记哪些字段是 NULL
    - **规则**：**逆序存放**，1 代表 NULL，0 代表非 NULL
    - **优化**：如果所有字段都定义为 `NOT NULL`，则**没有该结构**，节省 1 字节
    - 注意：**NULL值不是直接存储在真实数据中的**

3. **记录头信息** (Record Header)
    - 核心字段：
        - `delete_mask`：删除标记(逻辑删除，置 1)
        - `next_record`：单向链表指针，指向下一条记录
        - `record_type`：记录类型(普通 / 最小 / 最大 / B + 树节点)

##### 记录的真实数据
1. **隐藏列**(必须掌握)：
    - `row_id` (6 字节)：如果没有主键 / 唯一键，InnoDB 会生成此列作为聚集索引(二者取其一)
    - `trx_id` (6 字节)：事务 ID，标记数据归属
    - `roll_pointer` (7 字节)：回滚指针，用于 MVCC 回溯版本
2. **用户列**：
    - 定义的字段数据



#### varchar(n) 中 n 最大取值为多少？
- **核心限制**：一行记录总大小（(不包含 TEXT/BLOB 大对象)）不能超过 **65535 字节**。
- **计算公式**：`nmax​=65535−变长列表字节数−NULL列表字节数−其他隐藏字段开销`
- **经典案例**：
    - 场景：只有 1 个 `varchar(n)` 字段，字符集 ASCII (1 字符 = 1 字节)，允许 NULL。
    - 计算：
        1. 65535 (行最大限制)
        2. **- 2** (变长列表：因 ASCII 最大 65535>255，需 2 字节)
        3. **- 1** (NULL 列表：因允许 NULL，需 1 字节)
        4. **= 65532**
    - **结论**：`varchar(65532)` 是理论最大值，但实际建表时通常会失败（因为一行还要包含其他字段，实际最大通常为 65535 - 2 - 1 - 其他 = 65532 左右）。

#### 行溢出怎么处理？

- **背景**：当单个字段过大(如长文本)，导致 **16KB 页存不下** 一条记录时，触发行溢出。

|格式|处理方式|存储内容|性能|
|:--|:--|:--|:--|
|**Compact**|部分存储|真实数据处存 **前 768 字节** + 溢出页地址（20 字节）|读取需多次 I/O|
|**Dynamic**|**完全存储**|真实数据处**只存 20 字节指针**，完整数据存溢出页|**推荐**，避免碎片化|
|**Compressed**|完全存储|指针 + 压缩数据|省空间，耗 CPU|
