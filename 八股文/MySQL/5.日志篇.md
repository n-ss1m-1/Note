# undo log（回滚日志）
#### 定义
- undo log 是 **`InnoDB` 存储引擎层** 特有的日志，是实现事务**原子性**和 **MVCC的核心基础
#### 两大核心作用
##### 1.保障事务原子性(回滚)
1. **事务执行增删改操作**：InnoDB 会把**修改前的旧数据**记录到 undo log 中
    - `INSERT`：记录主键，回滚时执行 `DELETE`
    - `DELETE`：记录完整行数据，回滚时执行 `INSERT`
    - `UPDATE`：记录修改前的旧值，回滚时执行反向 `UPDATE`（主键列需先删后插）
2. **事务回滚**：沿着 undo log 逆向执行，将数据恢复到事务开始前的状态，保证「要么全成功，要么全失败」
3. **事务崩溃**：也会通过 undo log 回滚未提交的事务

##### 2.实现MVCC
- 每一行聚簇索引记录都有两个隐藏列：
    - `trx_id`：最后一次修改该记录的事务 ID
    - `roll_pointer`：回滚指针，指向该记录的上一个历史版本
- 每次修改都会生成新的 **undo log**，通过 **`roll_pointer`** **串联**成**版本链**
- 事务执行快照读（普通 `SELECT`）时，根据 **Read View 遍历版本链**，找到对当前事务可见的历史版本，实现无锁并发读，支撑「读已提交」「可重复读」隔离级别

#### 特性
- **逻辑日志**：记录的是操作的逆过程，不是物理数据页的修改
- **持久化机制**：undo log 写入 Buffer Pool 的 undo 页，其持久化由 **redo log** 保证（和数据页刷盘逻辑一致）
- **删除时机**：事务提交后不会立即删除，先标记delete flag，由 purge 线程在合适时机清理(不再被任何事务需要时)

#### undo log - Buffer Pool - redo log(怎么保证undo log的持久化)
- **undo log 生成**后，会写入 Buffer Pool 中的 **undo 页**
- undo 页的修改会**同步到 redo log**，通过 **redo log 的刷盘机制**保证 undo log 的持久化
- 事务提交、MySQL 宕机恢复时，undo log 的完整性由 redo log 兜底


# Buffer Pool（缓冲池）
#### 定义
Buffer Pool 是 `InnoDB` 存储引擎的**核心内存组件**，作用是将磁盘数据缓存在内存中，**大幅减少磁盘 I/O，提升 MySQL 读写性能**

#### 原理
- **页为单位缓存**：`InnoDB` 以「**页**」(默认 16KB)为磁盘和内存交互的基本单位，查询一条记录时，会将**整个数据页**加载到 Buffer Pool，再通过页目录定位具体记录
- ([[2.索引篇#InnoDB是怎么存储/查询数据的？|查询一条记录 -> 缓存一整个数据页]])
- **读写流程**：
    - **读**：数据命中 Buffer Pool 则直接读取，未命中则从磁盘加载到 Buffer Pool 再读取
    - **写**：修改数据时，仅修改 Buffer Pool 中的页（标记为「脏页」），不立即刷盘，由后台线程定期刷回磁盘，减少随机 I/O

#### 缓存内容
- 数据页（聚簇索引 / 非聚簇索引的完整数据）
- 索引页
- undo 页（undo log 存储页）
- 插入缓存页、自适应哈希索引、锁信息等




# redo log（重做日志）
#### 概述
- redo log（重做日志）是 **InnoDB存储引擎层** 特有的物理日志
- 核心作用：
	- 保障**事务的持久性**，实现 MySQL 的 crash-safe（崩溃恢复）能力
	- 通过 **WAL 技术**，将磁盘的**随机写**转化为**顺序写**，从而大幅提升写入性能

#### 日志类型
**物理日志**：
- 记录「**某个数据页上的具体修改**」（示例：id=1 的 balance 字段 + 100）
- **而非逻辑 SQL 语句**
#### 存储结构
- 由 2 个固定大小的循环文件组成（`ib_logfile0`、`ib_logfile1`），默认总大小 2GB
- **循环写入**：写满一个文件后切换到另一个，覆盖已完成脏页刷盘的旧日志，不会无限膨胀
- 环形结构通过 **`write pos`**（当前写入位置）和 **`checkpoint`**（可擦除位置）管理：
    - `write pos ~ checkpoint`：可写入新日志的区域
    - `checkpoint ~ write pos`：待刷盘的脏页对应的日志区域
    - 若 `write pos` 追上 `checkpoint`，触发 checkpoint 刷脏页，释放空间
- ![[redolog存储结构.PNG|343]]


#### 写入流程：WAL(Write-Ahead Logging 预写日志)
- **先写日志，再写数据**：
- 事务执行时：修改写入 Buffer Pool，同时生成 redo log 写入 `redo log buffer`(内存)
- 事务提交时，根据 `innodb_flush_log_at_trx_commit` 策略刷盘
- 后台线程定期将 redo log buffer 刷入 redo log file(-PageCache-磁盘)，同时异步刷脏页
	- ![[WAL技术的过程.PNG|468]]

#### 刷盘策略
1. **redo log buffer 空间占用超过 1/2 时**，主动刷盘
2. **MySQL 正常关闭时**，全量刷盘
3. **后台线程每秒定时刷盘**
4. 事务提交时根据**innodb_flush_log_at_trx_commit参数**策略->写入redo log file(Page Cache)和刷盘
	- 参数值=0：
		- 事务提交时不写入PageCache，后台线程每秒刷盘
		- MySQL崩溃时：丢失1s数据
	- 参数值=1：
		- 事务提交时写入PageCache+立即刷盘（fsync）
		- MySQL崩溃时：不会丢失数据
	- 参数值=2：
		- 事务提交时写入Page Cache，后台每秒刷盘
		- 不会丢失数据(已写入PageCache 操作系统崩溃或系统断电->才会丢失数据)

![[innodb_flush_log_at_trx_commit 的刷盘时机.PNG|640]]


**redo log 为什么可以在事务未提交时可以刷盘？**
- redo log**仅记录修改**，事务未提交时刷盘不影响数据一致性，宕机后通过binlog校验回滚
- binlog必须在事务提交后刷盘，否则会导致主从不一致


#### redo log 与 undo log 核心区别

| 维度          | redo log           | undo log           |
| ----------- | ------------------ | ------------------ |
| **核心作用**    | 事务持久性、崩溃恢复         | 事务原子性、回滚、MVCC      |
| **记录内容**    | 修改后的值（物理日志）        | 修改前的值（逻辑日志）        |
| **生命周期**    | 事务提交后，脏页刷盘后失效      | 事务提交后，purge 线程清理   |
| **写入log方式** | 顺序写、循环写            | 随机写、追加写            |
| **作用场景**    | 事务提交后宕机，通过 redo 恢复 | 事务未提交宕机，通过 undo 回滚 |

# binlog（归档日志）
#### 概述
- binlog（归档日志）是 **MySQL Server 层** 生成的逻辑日志，**所有存储引擎都支持**
- 核心作用：
	1. **数据备份与恢复**：记录所有数据变更，可用于误删数据恢复、全量 + 增量备份
	2. **主从复制**：主库将binlog同步给从库，从库重放实现数据同步，支撑读写分离、高可用架构
	3. **数据审计**：记录所有 DML/DDL 操作，用于问题排查、合规审计
> 注意：binlog **不记录查询类操作**（如 `SELECT`/`SHOW`），只记录数据变更。


#### binlog与redo log的区别
1. **所属层级**：
	- bin log： MySQL Server层，所有引擎通用
	- redo log：InnoDB存储引擎层，仅 InnoDB支持

2. **日志类型**：
	- bin log：逻辑日志（记录 SQL / 行变更），三种文件格式：
		1. STATEMENT(默认)：记录原始SQL语句，体积小，动态函数(now等)数据不一致
		2. ROW(推荐)：记录行数据最后被修改成什么，主从数据100%一致，体积大
		3. MIXED：自动选择上述两种格式
	- redo log：物理日志（记录数据页的具体修改）
		- 比如对X表空间中的Y数据页Z偏移量的地方做了A更新

3. **写入方式**：
	- bin log：追加写，永不覆盖，永久保存
	- redo log：循环写，覆盖已刷脏页的旧日志

4. **写入时机**：
	- bin log：**事务提交时**一次性写入
	- redo log：**事务执行过程中**持续写入

5. **核心作用**：
	- bin log：主从复制、数据备份恢复
	- redo log：事务持久性、崩溃恢复

6. **恢复能力**：
	- bin log：可恢复任意时间点全量数据
	- redo log：仅恢复宕机时未刷盘的脏页


#### 具体写入流程
1. **事务执行时**，将binlog写入 `binlog cache`（线程私有内存）
2. **事务提交时**，将 `binlog cache` 一次性刷入磁盘binlog文件(保证事务原子性，不可拆分)
3. **主从复制**：主库通过 `log dump` 线程将binlog同步给从库，从库写入 `relay log`（中继日志），再由 SQL 线程重放

#### 刷盘策略
- **事务提交时**，binlog就从binlog cache写入binlog file(**实际是写入PageCache中**)
- 通过**sync_binlog参数**，控制binlog**从PageCache刷入磁盘的时机**：
	- sync_binlog为0（默认）：每次提交事务只write，不fsync，后续交由操作系统决定何时将数据持久化到磁盘
	- sync_binlog为1：每次提交事务都会 立刻write+fsync刷盘
	- sync_binlog为N：每次提交事务都write，累积N个事务后才fsync刷盘
- 补充：
	- 只write，不fsync的风险：缓存在PageCache中，一旦主机异常重启，数据将丢失
	- 生产环境「**双 1 标准**」：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`，保证数据零丢失

#### bin log怎么实现主从复制？
##### 核心流程
1. **写入Binlog**：事务提交时主库写入binlog，`log dump`线程将binlog推送给从库
2. **同步Binlog**：从库I/O线程拉取主库 binlog，写入本地 `relay log`（中继日志）
3. **回放Binlog**：从库 SQL 线程重放 `relay log` 中的操作，同步数据到从库，实现主从一致
![[主从复制流程.PNG|553]]
##### 复制模式

| 模式           | 核心逻辑                       | 优缺点             |
| ------------ | -------------------------- | --------------- |
| **异步复制（默认）** | 主库提交事务不等待从库响应              | 性能最高，主库宕机可能丢数据  |
| **半同步复制**    | 主库等待至少一个从库确认接收 binlog 后再提交 | 数据安全高，性能略有损耗    |
| **同步复制**     | 主库等待所有从库同步完成后再提交           | 数据零丢失，性能极差，几乎不用 |
##### 最佳实践
- 主库推荐 2~3 个从库，避免从库过多消耗主库资源
- 从库用于**读流量分流**、**数据备份**，不直接承载写操作

# 两阶段提交
#### 定义
- 两阶段提交（Two-Phase Commit, 2PC）是 MySQL 为了**保证redo log和binlog两份日志的逻辑一致性**，实现的分布式事务一致性协议
- 核心目标是：**事务要么全成功，要么全失败，绝不出现半成功状态**

#### 为什么需要两阶段提交？
redo log(InnoDB层，崩溃恢复)和bin log(Server层，主从复制)是**两个独立的日志系统**，若不做一致性保证，会出现「**半成功**」导致**主从数据不一致**：
- 场景 1：redo log 刷盘成功，binlog 刷盘前宕机 → 主库数据更新成功，从库因无binlog未更新，主从不一致
- 场景 2：binlog刷盘成功，redo log刷盘前宕机 → 主库因redo log未完成回滚数据，从库因binlog已同步更新，主从不一致
两阶段提交通过「**prepare + commit**」两个阶段，强制两份日志的状态对齐，彻底解决问题


#### 两阶段提交流程(内部 XA 事务)
MySQL 以binlog为协调者，InnoDB存储引擎为参与者，分两个阶段完成事务提交：

##### 1. Prepare 阶段（准备阶段）
1. InnoDB层将事务的 XID（内部事务 ID）写入 redo log，将 redo log 事务状态设为 `prepare`
2. 将redo log持久化刷入磁盘（`innodb_flush_log_at_trx_commit=1` 生效）
3. 向Server层返回「prepare 成功」的响应

##### 2. Commit 阶段（提交阶段）
1. Server层将 XID 写入 binlog，将binlog持久化刷入磁盘（`sync_binlog=1` 生效）
2. 调用InnoDB引擎的提交事务接口，将redo log事务状态设为 `commit`
3. 事务正式提交完成，返回客户端「操作成功」
![[两阶段提交流程.PNG|571]]


#### 系统异常重启的崩溃恢复逻辑
MySQL 重启时，会扫描所有处于 `prepare` 状态的redo log，通过 **XID 校验**binlog状态，自动完成事务的提交 / 回滚：

- **redo log刷盘成功，binlog 未刷盘时刻 宕机**：binlog中无对应 XID → 回滚事务
- **redo log、binlog均刷盘成功，未完成 commit时刻 宕机**：binlog中有对应 XID → 提交事务

> 核心设计：**以binlog写入成功作为事务提交的最终标识**，保证主库和从库的数据一致性。


#### 两阶段提交的问题与优化
##### 问题
- **磁盘 I/O 次数高**：「双 1」配置下，每个事务提交需执行 2 次 `fsync`（redo log刷盘 + binlog刷盘），高并发下成为性能瓶颈
- **锁竞争激烈**：多事务场景下，需加锁保证提交顺序，锁粒度大，并发性能差

##### 优化：组提交
- **原理**：
- 将**多个事务的提交操作合并**，**批量刷盘**，大幅减少 `fsync` 次数，提升并发性能
- 组提交将 commit 阶段拆分为 3 个**队列**，细化锁粒度，支持阶段并行

| 阶段            | 核心操作                                    | 优化点                                     |
| ------------- | --------------------------------------- | --------------------------------------- |
| **Flush 阶段**  | **按顺序**将redo log+binlog写到PageCache(不刷盘) | MySQL 5.7+支持redo log组提交减少 redo log 刷盘次数 |
| **Sync 阶段**   | 批量对redo log+binlog执行 `fsync` 刷盘         | 多个事务合并一次刷盘，将 N 个事务的刷盘时间从 N 降为 1         |
| **Commit 阶段** | 按顺序调用InnoDB提交接口，将redo log设为 `commit` 状态 | 快速完成提交，不阻塞后续事务                          |

- **组提交的可调参数**
	- `binlog_group_commit_sync_delay=N`：等待 N 微秒后再刷盘，组合更多事务
	- `binlog_group_commit_sync_no_delay_count=N`：队列中事务数达到 N 个，立即刷盘，忽略延迟
	- 生产推荐：结合两个参数，平衡延迟与刷盘次数，提升吞吐量



# update 语句完整执行流程
具体更新一条记录 `UPDATE t_user SET name = 'xiaolin' WHERE id = 1;` 的流程如下:

1. 执行器负责具体执行，会调用存储引擎的接口，通过主键索引树搜索获取 `id = 1` 这一行记录：
    - 如果 `id=1` 这一行所在的数据页本来就在 `buffer pool` 中，就直接返回给执行器更新；
    - 如果记录不在 `buffer pool`，将数据页从磁盘读入到 `buffer pool`，返回记录给执行器。
    
2. 执行器得到聚簇索引记录后，会看一下更新前的记录和更新后的记录是否一样：
    - 如果一样的话就不进行后续更新流程；
    - 如果不一样的话就把更新前的记录和更新后的记录都当作参数传给 `InnoDB` 层，让 `InnoDB` 真正的执行更新记录的操作；
    
3. 开启事务，`InnoDB` 层更新记录前，首先要记录相应的 `undo log`，因为这是更新操作，需要把被更新的列的旧值记下来，也就是要生成一条 `undo log`，`undo log` 会写入 `Buffer Pool` 中的 `Undo` 页面，不过在内存修改该 `Undo` 页面后，需要记录对应的 `redo log`。
    
4. `InnoDB` 层开始更新记录，会先更新内存（同时标记为脏页），然后将记录写到 `redo log` 里面，这个时候更新就算完成了。为了减少磁盘 I/O，不会立即将脏页写入磁盘，后续由后台线程选择一个合适的时机将脏页写入到磁盘。这就是 **WAL 技术**，MySQL 的写操作并不是立刻写到磁盘上，而是先写 `redo` 日志，然后在合适的时间再将修改的行数据写到磁盘上。
    
5. 至此，一条记录更新完了。
    
6. 在一条更新语句执行完成后，然后开始记录该语句对应的 `binlog`，此时记录的 `binlog` 会被保存到 `binlog cache`，并没有刷新到硬盘上的 `binlog` 文件，在事务提交时才将binlog写入binlog file(实际是写入PageCache中)，具体何时刷盘依据选择的策略。
    
7. 事务提交（为了方便说明，这里不说组提交的过程，只说两阶段提交）：
    - **prepare 阶段**：将 `redo log` 对应的事务状态设置为 `prepare`，然后将 `redo log` 刷新到硬盘；
    - **commit 阶段**：将 `binlog` 刷新到磁盘，接着调用引擎的提交事务接口，将 `redo log` 状态设置为 `commit`（将事务设置为 `commit` 状态后，刷入到磁盘 `redo log` 文件）；
    
8. 至此，一条更新语句执行完成。
