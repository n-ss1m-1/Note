# 索引基础
#### 什么是索引？
- 索引就像书的目录
- 索引是帮助存储引擎快速获取数据的**有序数据结构**，索引和数据都存储在**存储引擎层**
- **空间换时间**：用额外的索引结构，牺牲少量写入性能(维护索引)，大幅提升查询效率

#### 索引的分类
##### 按数据结构分类

| 索引类型                     | 数据结构  | 核心特点                                                                                             | 存储引擎支持                                                        | 适用场景       |
| :----------------------- | :---- | :----------------------------------------------------------------------------------------------- | :------------------------------------------------------------ | :--------- |
| **B+Tree 索引(InnoDB 默认)** | 多叉平衡树 | 1. 非叶子节点仅存索引，叶子节点存数据 / 主键<br><br>2. 叶子节点双向链表，保证全局有序<br><br>3. 支持**等值 + 范围查询**，千万级数据仅需 3-4 次磁盘 IO | InnoDB<br><br>MyISAM<br><br>Memory                            | 所有业务场景     |
| **HASH 索引**              | 哈希表   | 1. 等值查询 O (1) 极快<br><br>2. **不支持范围查询、排序**                                                        | Memory(原生支持)<br><br>InnoDB(仅支持自适应哈希索引 AHI)<br><br>MyISAM(不支持) | 仅高频等值查询场景  |
| **Full-Text索引(全文索引)**    | 倒排索引  | 支持长文本模糊匹配、全文搜索                                                                                   | InnoDB(5.6 + 支持)<br><br>MyISAM<br><br>Memory(不支持)             | 长文本、文章搜索场景 |

##### 按物理存储分类
###### 1. 聚簇索引(主键索引)
- 核心特点：索引与数据绑定，**叶子节点存储完整行数据**；一个表**只能有 1 个**聚簇索引
- InnoDB聚簇索引的生成规则：
    1. 有主键：默认用主键作为聚簇索引 key
    2. 无主键：选择第一个非空唯一列作为聚簇索引 key
    3. 都无：自动生成 6 字节隐式自增`row_id`作为聚簇索引 key

###### 2. 二级索引(辅助索引 / 非聚簇索引)
- 核心特点：索引与数据分离，**叶子节点仅存主键值**，不是实际数据；一个表可以有多个
- 核心流程：查询时先查二级索引拿到主键，再**回表查询**聚簇索引获取完整数据


##### 按字段特性分类
###### 1. 主键索引
- 定义：建立在主键字段上的索引，**唯一、非空**，是聚簇索引，一个表最多 1 个
- 建表时创建：`PRIMARY KEY (id) USING BTREE;`

###### 2. 唯一索引
- 定义：建立在`UNIQUE`字段上的索引，索引值唯一，允许空值(非主键)，一个表可以有多个
- 创建方式：
```
-- 建表时创建
UNIQUE KEY (column1, column2...)

-- 建表后创建
CREATE UNIQUE INDEX idx_name ON table_name(column1, column2...);
```

###### 3. 普通索引
- 定义：普通字段上的索引，无唯一性要求，最常用
- 创建方式：
 ```
 -- 建表时创建
INDEX (column1, column2...)
    
-- 建表后创建
CREATE INDEX idx_name ON table_name(column1, column2...);
 ```

###### 4. 前缀索引

- 定义：对字符串类型字段的**前 N 个字符**建索引，减少索引空间、提升查询效率
- 适用场景：长字符串（如 URL、邮箱）
- 创建方式：
``` 
-- 建表时创建
INDEX (column_name(length))

-- 建表后创建
CREATE INDEX idx_name ON table_name(column_name(length));
```

##### 按字段个数分类
###### 1. 单列索引
- 定义：单个字段上的索引，比如主键索引、普通单列索引

###### 2. 联合索引(复合索引)
- 定义：多个字段组合成的索引，**遵循最左匹配原则**
- 结构逻辑：B + 树按索引列顺序排序，先按第一个字段排序，第一个字段相同再按第二个......


#### 什么时候需要/不需要创建索引？
###### 索引的优点
- 大幅提升查询速度，优化排序 / 分组，实现唯一性约束
###### 索引的缺点
- 占用物理存储空间，数据量越大，索引占用越多
- 创建 / 维护索引耗时，数据量越大，维护成本越高
- 降低表的增删改效率：每次增删改都要动态维护 B + 树的有序性

###### 需要索引的场景
- **字段有唯一性限制**：如商品编码、身份证号，用唯一索引保证数据唯一性，同时加速查询
- **经常用于`WHERE`查询条件的字段**：单字段建单列索引，多条件组合建**联合索引**
- **经常用于`GROUP BY`和`ORDER BY`的字段**：利用 B + 树的天然有序性，避免额外排序操作

###### 不需要索引的场景
- **`WHERE`/`GROUP BY`/`ORDER BY`用不到的字段**：用不到的字段建索引只会浪费空间
- **存在大量重复数据的字段**：性别、状态(仅 2-3 种取值)，优化器会直接忽略索引走全表扫描
- **表数据太少的场景**：如几千行的小表，全表扫描比索引查询更快，无需建索引
- **频繁更新的字段**：维护 B + 树有序性需要频繁调整，严重影响增删改性能


#### 优化索引的方法
##### 1. 前缀索引优化
- **原理**：对字符串类型字段的**前 N 个字符**建索引，大幅减少索引大小，提升查询效率
- **适用场景**：长字符串字段（如 URL、邮箱、长文本）
- **局限性**：无法用于`ORDER BY`排序、无法作为覆盖索引

##### 2. 覆盖索引优化（核心必背）
- **原理**：查询的所有字段，完全包含在二级索引的 B + 树叶子节点中，**无需回表查询聚簇索引**
- **适用场景**：高频查询仅需部分字段，不需要全表数据
- **识别标志**：`EXPLAIN`执行计划中`Extra`字段显示`Using index`

##### 3. 主键索引最好是自增的（InnoDB 核心优化）
- **原理**：InnoDB主键是聚簇索引，自增主键保证插入有序，**避免页分裂**：
    - 自增主键：插入时追加到当前页末尾，页满直接开辟新页，无页分裂，写入性能极高
    - 非自增主键(如 UUID)：随机插入导致频繁页分裂，移动数据、产生内存碎片，性能低
- **补充**：主键字段尽量短小，主键越短->二级索引叶子节点越小，占用空间越少

##### 4. 索引最好设置为`NOT NULL`
- **原因 1**：`NULL`会干扰优化器的索引选择，导致索引统计、比较逻辑更复杂，`count`会忽略`NULL`行
- **原因 2**：`NULL`会占用物理空间，行格式中至少用 1 字节存储`NULL`值列表，浪费存储空间
- **建议**：设计表时，尽量给字段加`NOT NULL`约束，除非业务必须存储`NULL`

##### 5. 防止索引失效（面试高频，必背全场景）
索引失效的核心原因：**破坏 B + 树的有序性**，常见场景：
- 左 / 左右模糊匹配：`like %xx` 或 `like %xx%`
- 索引列做计算、函数、类型转换：如`YEAR(create_time)=2024`、`id+1=10`、字符串字段用数字查询
- 联合索引不遵循**最左匹配原则**：跳过最左列，如`(a,b,c)`索引，查询`where b=2`
- `OR`条件前后不全是索引列：`OR`前是索引，`OR`后不是，索引失效
- 负向查询：`!=`、`NOT IN`等，优化器会走全表扫描

##### 面试总结
- **索引的适用与不适用场景**：
    索引本质是空间换时间，优点是加速查询，缺点是占用空间、降低增删改效率。
    适用：唯一性字段、频繁`WHERE`查询、`GROUP BY`/`ORDER BY`的字段；
    不适用：用不到的字段、低区分度（如性别）、数据量少、频繁更新的字段。
- **索引优化方法**：
    用前缀索引减少长字符串索引空间；用覆盖索引避免回表，减少 IO；自增主键避免页分裂，提升写入性能；索引设为`NOT NULL`，优化器选择更高效；同时严格避免索引失效场景，比如左模糊、索引列计算、违反最左匹配等。
- **验证方法**：
    用`EXPLAIN`分析执行计划，重点看`type`（避免全表扫描`ALL`）、`key`（是否命中索引）、`Extra`（是否用覆盖索引、避免`filesort`）。


# 从数据页的角度看B+树

#### InnoDB是怎么存储/查询数据的？
##### 数据页的定义 
- InnoDB磁盘 I/O 的**最小单位是数据页**，默认大小 16KB，读写以页为单位整体读入 / 刷出内存，避免按行读写导致的低效 I/O，是「以页换时间」的设计。

##### 数据页的7大组成结构

| 组成部分                            | 大小    | 核心作用                                          |
| :------------------------------ | :---- | :-------------------------------------------- |
| **文件头（File Header）**            | 38 字节 | **页的元信息**，包含双向链表指针，连接上下页，保证页间逻辑连续（物理不连续，逻辑连续） |
| **页头（Page Header）**             | 56 字节 | **页的状态信息**，管理页内记录的单向链表结构                      |
| **最小 / 最大记录（Infimum+Supremum）** | 26 字节 | 两个虚拟伪记录，标记页内记录的边界，方便链表遍历                      |
| **用户记录（User Records）**          | 不确定   | 存储**实际行数据**，按主键顺序组成单向链表                       |
| **空闲空间（Free Space）**            | 不确定   | 页内**未使用的空间**，插入新记录时动态分配                       |
| **页目录（Page Directory）**         | 不确定   | **页内的「目录」**，存储记录分组的偏移量，用于二分查找快速定位记录           |
| **文件尾（File Trailer）**           | 8 字节  | 校验页是否完整，防止页损坏                                 |

##### 页目录：页内查询的核心优化
- **问题**：页内记录按主键组成单向链表，直接遍历时间复杂度 `O(n)`，效率极低
- **优化**：将页内记录**分组**(槽，slot)，每个槽存储组内最后一条记录的偏移量，通过**二分查找**快速定位槽，再遍历组内记录，将页内查询复杂度降到 `O(logn)`
- **分组规则**：第 1 组 1 条记录，最后 1 组 1-8 条，中间组 4-8 条，保证二分查找效率

#### B+树是如何进行查询的？
##### B+树的核心特点(面试必背)
- **节点存储差异**：仅**叶子节点**存储数据(或主键)，非叶子节点仅存索引(目录项)(->一个非叶子节点可用存放更多的目录项)，大幅降低树高，减少磁盘 I/O 次数
- **树高稳定**：千万级数据量下，树高稳定在 3-4 层，一次查询仅需 3-4 次磁盘 I/O
- **天然有序**：所有节点按索引键排序，叶子节点双向链表，完美支持范围查询(>/</between)

##### B+树的完整查询流程
- **从根节点开始 → 二分查找定位到对应数据页 → 逐层下推到叶子节点 → 通过页目录二分查找定位记录组 → 遍历组内记录找到目标数据**





# 为什么MySQL采用B+树作为索引？

#### 索引需要怎样的数据结构？
MySQL 数据持久化在磁盘，**磁盘 I/O 是性能的核心瓶颈**，因此好的索引结构必须满足两个硬性要求：
-  1. 尽可能**减少磁盘 I/O 操作次数**（树高越低越好，每次查询的 I/O 次数越少）
-  2. 同时高效支持**等值查询**和**范围查询**（MySQL 业务场景高频范围查询）

#### 二分查找(有序数组)
- 优点：查询时间复杂度 `O(logn)`，效率高
- 缺点：插入 / 删除 `O(n)`，磁盘上**插入需要移动大量数据**，完全不适合动态数据
- 结论：不适合作为索引结构

#### 二分查找树(BST)
- 优点：解决插入问题，天然支持二分查找，查询 `O(logn)`
- 缺点：
	- 极端情况(如递增插入) **退化成链表**，查询复杂度 `O(n)`
	- 树高不可控，磁盘 I/O 次数多
- 结论：无法保证稳定性能，不适合

#### 自平衡二叉树(AVL树、红黑树)
- 优点：解决 BST 退化成链表的问题，保持 `O(logn)` 高度，查询稳定
- 缺点：
	- 本质是二叉树，每个节点仅存 2 个子节点，**数据量越大树越高，磁盘 I/O 次数越多**
	- 不支持高效范围查询
- 结论：树高随数据量增长，I/O 次数多，不适合海量数据

#### B树(多叉平衡树)
- 优点：多叉树降低树高，减少 I/O 次数，支持范围查询
- 缺点：
	- **非叶子节点同时存索引 + 数据**，单个节点存储的索引数量少，树高仍偏高
	- 叶子节点无链表，**范围查询需遍历树**，效率低
	- **插入删除需调整非叶子节点**，效率低
- 结论：仍有优化空间，不是最优解

#### B+树
##### B+树的核心设计
1. **非叶子节点仅存索引**：非叶子节点不存实际数据，仅存索引，单个节点可存储更多索引，树更「矮胖」，磁盘 I/O 次数大幅减少
2. **叶子节点双向链表**：所有叶子节点用双向链表连接，天然全局有序，完美支持范围查询
3. **冗余索引优化**：非叶子节点都是冗余索引，插入 / 删除仅需调整叶子节点，非叶子节点自动平衡，插入删除效率远高于 B 树，无复杂树变形
4. **节点即数据页**：InnoDB中 B + 树的每个节点都是 16KB 的数据页，和磁盘 I/O 最小单位对齐，读写效率更高

##### B+树 vs B树

| 对比维度        | B 树                             | B + 树                            |
| :---------- | :------------------------------ | :------------------------------- |
| **节点存储内容**  | 非叶子节点存「**索引 + 数据**」             | 非叶子节点仅存「**索引**」，叶子节点存**数据**      |
| **树高与 I/O** | 非叶子节点存数据，单个节点索引少，树高更高，I/O 次数多   | 非叶子节点仅存索引，树更矮胖，I/O 次数更少          |
| **范围查询**    | 叶子节点无链表，**范围查询需遍历树**，多次 I/O，效率低 | 叶子节点**双向链表**，范围查询直接遍历链表，范围查询效率极高 |
| **插入删除效率**  | **需调整非叶子节点**，易引发复杂树变形，效率低       | **仅调整叶子节点**，非叶子节点自动平衡，效率高        |
| **冗余节点**    | 无冗余节点，删除易引发树结构变化                | 非叶子节点都是冗余索引，删除无复杂变形              |

##### InnoDB中B+树的专属特性
- 聚簇索引：叶子节点存储**完整行数据**，一个表仅 1 个
- 二级索引：叶子节点仅存储**主键值**，查询需回表，覆盖索引可避免回表
- **叶子节点双向链表**：支持双向遍历，范围查询、排序更高效
- 数据页默认 16KB：和磁盘 I/O 最小单位对齐，读写性能最优


#### 面试总结
从索引结构的要求、各类结构的缺陷、B + 树的优势三方面回答：
1. **好的索引结构要求**：数据存在磁盘，必须尽可能少的磁盘 I/O，同时支持等值和范围查询。
2. **其他结构的缺陷**：
    - 二分查找插入低效，二叉查找树易退化成链表，自平衡二叉树树高随数据量增长，I/O 次数多；
    - B 树非叶子节点存数据，树高偏高，范围查询效率低，插入删除效率低。
3. **B + 树的优势**：
    - 非叶子节点仅存索引，树更矮胖，磁盘 I/O 次数更少；
    - 叶子节点双向链表，天然有序，范围查询效率极高；
    - 冗余索引让插入删除仅调整叶子节点，效率远高于 B 树；
    - 完美适配InnoDB 16KB 数据页的存储结构，是 MySQL 最优索引结构。



# 索引失效的场景有哪些？
#### 索引的存储结构
- **InnoDB索引结构**：
	- **叶子节点存储内容**：
		- 聚簇索引：完整行数据
		- 二级索引：主键值
	- **索引类型**：聚簇索引+二级索引
	- **特点**：二级索引查询需回表(2次查询)，覆盖索引可以避免回表
- **MyISAM索引结构**：
	- **叶子节点存储内容**：数据的物理递增
	- **索引类型**：全为二级索引
	- **特点**：无回表，直接通过地址取获取完整行数据

- **两个核心流程**
	1. **回表**：
		- 先查二级索引的B+树，获取主键值
		- 再查聚簇索引的B+树，获取完整行数据
	2. **覆盖索引**：查询字段完全包含在二级索引中，无需回表(1次查询)

#### 索引失效的根本原因
- **破坏了 B + 树索引的有序性**，导致无法利用二分查找快速定位数据，最终只能全表扫描

#### 6种高频索引失效场景
##### 1. 左 / 左右模糊匹配(`like %xx` / `like %xx%`)
- **现象**：`EXPLAIN`中`type=ALL`，全表扫描
- **原因**：
	- B + 树按索引值**前缀有序**存储，只能根据前缀快速比较
	- 左模糊无法确定前缀，只能全表遍历
- **反例**：`select * from t_user where name like '%林';`(左模糊，索引失效)
- **正例**：`select * from t_user where name like '林%';`(**右模糊**，走`range`索引)
- **解决**：**避免左模糊**，长文本模糊查询用**全文索引**替代

##### 2. 索引列使用函数
- **现象**：`type=ALL`，全表扫描
- **原因**：索引存储的是**原始值**，不是函数计算后的值，无法走索引
- **反例**：`select * from t_user where length(name)=6;`
- **解决**：
    - MySQL 8.0+：创建**函数索引**
		- `alter table t_user add key idx_name_length ((length(name)));`
    - 通用方案：将计算逻辑移到业务层，避免在索引列用函数

##### 3. 索引列进行表达式计算
- **现象**：`type=ALL`，全表扫描
- **原因**：索引存原始值，无法对计算后的值走索引
- **反例**：`select * from t_user where id + 1 = 10;`(对 id 列做计算，失效)
- **正例**：`select * from t_user where id = 10 - 1;`(计算移到等式右侧，不操作索引列，走索引)
- **解决**：避免在索引列做计算，将计算逻辑移到条件右侧

##### 4. 隐式类型转换
- **现象**：`type=ALL`，全表扫描
- **原因**：MySQL 遇到字符串和数字比较时，自动将**字符串转数字**(相当于对索引列使用`CAST`函数)，导致索引失效
- **关键区分（面试易错）**：
    - ❌ 索引列是字符串，参数是数字：`where phone = 1300000001;`
	- （phone 是 varchar，自动转换为数字，索引失效）
    - ✅ 索引列是数字，参数是字符串：`where id = '1';`
    - （id 是 `bigint`，不自动转换为字符串，索引不失效，转换的是`1`）
- **解决**：查询参数类型与索引列类型严格一致，避免隐式转换

##### 5. 联合索引不遵循最左匹配原则
- **现象**：`type=ALL`或仅部分索引生效
- **原因**：联合索引必须从**声明创建索引**的最左字段开始匹配(否则不生效)，**连续无跳过(否则后半部分失效)**，**where中书写的条件顺序不影响**(优化器自动调整顺序)
- **生效场景**：`where a=1 and b=2 and c=3`、`where c=3 and a=1 and b=2`
- **失效场景**：`where b=2`、`where c=3`(完全失效)、`where a=2 and c=3`（后半部分失效）
- **特殊说明**：MySQL 5.6 + 的**索引下推**，可在存储层过滤部分条件，减少回表，但不代表索引生效
- **解决**：严格遵循最左匹配，联合索引按查询频率排序字段

##### 6. WHERE 子句中的 OR 条件
- **现象**：`type=ALL`，全表扫描
- **原因**：OR 只要有一个条件不是索引列，就会全表扫描
- **反例**：`select * from t_user where id = 1 or age = 18;`（id 是主键，age 无索引）
- **解决**：
    - 给 OR 后的字段加索引
    - 用`UNION ALL`拆分查询：`select * where id=1 union all select * where age=18;`


#### 索引失效的验证方法
用 **EXPLAIN 分析执行计划**，核心看 2 个关键字段：
- `type`：数据扫描类型
	- `ALL`代表全表扫描（索引失效）
	- `range`/`ref`/`eq_ref`/`const`代表走索引（性能从低到高）
- `key`：实际使用的索引
	- `NULL`说明未使用索引
	- `key_len`可判断联合索引用了多少列


# 不同的`count()`之间有什么区别？
#### 核心结论
![[count的性能排序.PNG|521]]

#### count 函数本质
- `count()` 是聚合函数，作用是**统计符合查询条件的记录中，参数不为 NULL 的行数**：
	- `count(字段)`：统计**该字段不为 NULL** 的行数（字段为 NULL 不统计）
	- `count(1)` / `count(*)`：统计**所有行数**（1 是常量，永远不为 NULL；`*` 被 MySQL 优化为常量 0 处理，等价于 `count(1)`）
	- `count(主键字段)`：统计主键不为 NULL 的行数（主键天然非空，等价于统计总行数）


#### 不同 count 的执行过程
##### 1. `count(1)` 执行过程
- 遍历**最小的二级索引树**（无二级索引则遍历主键索引树）
- 仅读取索引节点，**不读取实际行数据**，直接判断 1 不为 NULL ，count 变量 +1
- 步骤最少，性能极高

##### 2. `count(*)` 执行过程
- MySQL 会将 **`*` 优化为常量 0 处理**，执行逻辑、性能**完全等价于 `count(1)`**；
- 同样遍历最小二级索引树，不读取行数据，性能最优。

##### 3. `count(主键字段)` 执行过程
- 遍历二级索引树，读取主键值；
- 判断主键不为 NULL（主键天然非空），count 变量 +1；
- 比 `count(1)`/`count(*)` 多一步「**读取主键值**」，性能略低。

##### 4. `count(普通字段)` 执行过程
- 若字段无索引：**全表扫描(type=ALL)**，**读取每一行的字段值**，判断是否为 NULL，再计数
- 若字段有索引：遍历该字段的二级索引树，读取字段值判断非空，再计数
- 性能最差，仅用于统计「该字段非空行数」的业务场景

#### 为什么InnoDB必须遍历计数？
#### `count(*)`：`InnoDB vs MyISAM`

| 存储引擎       | `count(*)` 执行逻辑                          | 性能差异    |
| ---------- | ---------------------------------------- | ------- |
| **MyISAM** | 表级锁保证一致性，直接读取表的 `row_count` 元信息，O(1) 复杂度 | 极快，无需遍历 |
| **InnoDB** | 多版本并发控制（MVCC），无法维护全局准确行数，必须遍历索引树计数       | 慢，需遍历索引 |

#### `count(*)` 优化方案
##### 1. 近似值方案（适合非精确统计）
- 用 `EXPLAIN SELECT count(*) FROM 表名;`   `rows` 字段为估算值
- 优点：毫秒级返回，无需真实查询
- 缺点：仅为估算值，不精确

##### 2. 精确值方案（适合需要精确统计）
- 新增**计数表**，在业务插入 / 删除数据时，同步维护计数表的计数字段
- 优点：查询计数表 O(1) 复杂度，性能极高
- 缺点：需要额外维护计数表的一致性（可通过事务 / 触发器保证）



# MySQL分页有什么性能问题？怎么优化？

#### 为什么分页越往后越慢
- **根本原因**：`LIMIT offset, size` 的执行逻辑是，先逐行读取数据，判断是否符合条件，符合则计数，直到**读取 `offset+size` 条数据，丢弃前 `offset` 条，只返回最后 `size` 条**。
- **主键索引**：叶子节点存完整行数据
- **非主键索引**：
	- 叶子节点存主键，需要**回表**查询完整数据，性能更差。
	- 当 `offset` 极大时，非主键索引甚至会触发**全表扫描**(优化器认为回表成本太高，直接放弃索引)

#### 深度分页问题
######  定义
当 `offset` 达到**百万级**时，`LIMIT offset, size` 的性能会急剧恶化，甚至耗时数秒，这就是「深度分页问题」。
###### 本质
深度分页的核心是**大量无效数据的读取与丢弃**，且无法通过索引直接定位到 `offset` 位置(因为无法判断某行是否符合条件)，只能逐行遍历，属于「无解问题」，只能通过方案规避。


#### 分页优化方案
##### 1.主键索引分页
- **原理**：主键索引是聚簇索引，叶子节点存完整行数据，无需回表，直接遍历索引，性能远高于非主键索引。
- 示例：`select * from page order by id limit 0,10;`（走主键索引，性能最优）
- 注意：非主键索引分页会多一次回表，`offset` 极大时甚至全表扫描，**尽量用主键分页**。

##### 2.子查询优化
- 原理：先通过索引快速定位到 `offset` 位置的主键，再用主键查询完整数据，避免读取大量无效行。
- 优化前（慢）：
	`select * from page order by id limit 600000,10;`
- 优化后（快）：
```
	select * from page 
	where id >= (select id from page order by id limit 600000, 1) 
	order by id limit 10;
```

- 优势：**子查询只读取主键，不读取完整行**，大幅减少 I/O，性能提升 1 倍以上。


##### 基于起始ID的游标分页
- **原理**：**彻底抛弃 `LIMIT offset, size`，用「上一页最大 ID」作为分页条件，每次从该 ID 后取 `size` 条数据**。

- **示例**：
```
-- 第一页：start_id=0
select * from page where id > 0 order by id limit 100;

-- 第二页：取上一页最大ID=100，作为起始条件
select * from page where id > 100 order by id limit 100;

-- 第N页：start_id=上一页最大ID
select * from page where id > :start_id order by id limit 100;
```

**核心优势**：
- 无论数据量多大，每次查询都通过主键索引**快速定位**，性能稳定，耗时始终毫秒级；
- 彻底避免了「读取并丢弃大量无效数据」的问题，从根源解决深度分页。

**适用场景**：
- 产品设计为**上一页 / 下一页**（不支持跳页），如抖音、小红书的瀑布流；
- 不支持跳页的用户分页场景，是生产环境最优方案。
